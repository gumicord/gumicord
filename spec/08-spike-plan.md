## 目的

[ADR-0001](adr/0001-native-rust-renderer.md) で Rust 自前レンダラを選んだ結果、**未検証の前提の上に仕様全体が乗っている**状態にある。詳細仕様 (`03`〜`07`) を書く前に、前提を実測で潰す。

スパイクのコードは**捨てる前提**である。成果物はコードではなく、**ADR に追記される測定値と判断**である。

## 原則

1. **リスクの高い順に潰す。** 最も「不可能かもしれない」ものから着手する
2. **1 スパイク 1 仮説。** 何を確かめたいのかを先に書く
3. **Go/No-Go を先に決める。** 着手前に合格基準を定義し、後から基準を緩めない
4. **結果は必ず記録する。** 失敗も記録する。「やってみたが忘れた」を残さない

## 実行順序とリスク

```
S0 ツールチェーン導入
   │
   ▼
S1 ウィンドウ + カスタムタイトルバー + 性能実測    リスク: 中
   │     └─ NFR-001, NFR-002, PLT-020, PLT-021 の根拠を作る
   ▼
S2 IME + アクセシビリティ                        リスク: 最高 ★
   │     └─ ここが駄目なら ADR-0001 ごと見直し
   ▼
S3 QuickJS 組み込み                              リスク: 低〜中
   │     └─ ADR-0002 の検証
   ▼
S4 Gateway 接続                                  リスク: 低
         └─ プロトコル仕様執筆の前提を確認
```

## S1. ウィンドウ + カスタムタイトルバー + 性能実測

### 仮説

> `winit` + `wgpu` で、OS 標準のタイトルバーを排した独自ウィンドウを作り、公式 Discord より小さいメモリと速い起動を達成できる。

### 検証すること

| # | 内容 | 関連要件 |
|---|---|---|
| 1-1 | `winit` + `wgpu` でウィンドウを出し、角丸矩形とテキストを描画する | — |
| 1-2 | OS 標準タイトルバーを消し、独自描画のタイトルバーに置き換える | `PLT-020` |
| 1-3 | 独自タイトルバーで、ドラッグ移動・ダブルクリック最大化・スナップ・システムメニューが OS 標準と等価に動く | `PLT-021` |
| 1-4 | ウィンドウ非アクティブ時に描画を止め、CPU 使用率が下がる | `NFR-005` |
| 1-5 | DPI スケール変更とディスプレイ間移動に追従する | `PLT-009` |
| 1-6 | 2D 描画方式を比較する: **自前バッチャ** / `vello` / `skia-safe` | — |

### 計測項目

同一マシン・同一条件で、**公式 Discord デスクトップ版と並べて測る**。比較対象がない数値には意味がない。

| 指標 | 測り方 (Windows) |
|---|---|
| コールドスタート | プロセス起動から最初のフレーム提示まで。`QueryPerformanceCounter` で自己計測 |
| 常駐メモリ | アイドル 60 秒後の Working Set と Private Bytes。`Get-Process` |
| アイドル CPU | 非アクティブ 60 秒間の平均 CPU 使用率 |
| フレーム時間 | スクロール中の p50 / p99。自己計測 |
| バイナリサイズ | release ビルド (LTO + strip) の実サイズ |

### Go/No-Go

| 条件 | 判定 |
|---|---|
| 常駐メモリが公式クライアントを下回る | **必須** |
| コールドスタートが公式クライアントを下回る | **必須** |
| 独自タイトルバーが `PLT-021` の 4 挙動すべてを満たす | **必須** |
| スクロールの p99 フレーム時間がリフレッシュ周期に収まる | 必須 (`NFR-003`) |

いずれかを満たせない場合、原因を特定して再試行する。3 回試して達成できなければ ADR-0001 を見直す。

### 成果物

- `spike/s1-window/` (捨てるコード)
- ADR-0001 への追記: 実測値、2D 描画方式の決定と根拠
- `01-requirements.md` の `NFR-001`, `NFR-002` の数値を実測に基づいて確定

## S2. IME + アクセシビリティ ★最高リスク

### 仮説

> 自前レンダラのテキスト入力欄で、日本語をインライン変換で入力できる。かつ、OS のスクリーンリーダーが UI を読み上げられる。

**これが成立しなければ、Gumicord はチャットクライアントとして成立しない。** ADR-0001 の見直し条件に直結する。

### 検証すること

| # | 内容 | 関連要件 |
|---|---|---|
| 2-1 | テキスト入力欄を自前で実装する (キャレット・選択範囲・折り返し) | — |
| 2-2 | **未確定文字列 (preedit) を下線付きで表示する** | `PLT-001` |
| 2-3 | **変換候補ウィンドウが正しい位置に出る** (キャレット直下) | `PLT-001` |
| 2-4 | 変換確定・変換取り消し・部分変換が正しく動く | `PLT-001` |
| 2-5 | 日本語 / 中国語 / 韓国語で 2-2〜2-4 を確認する | `PLT-002` |
| 2-6 | `accesskit` でアクセシビリティツリーを公開し、ナレーターが読み上げる | `PLT-003` |
| 2-7 | **`accesskit` の iOS 対応状況を調査する** | `PLT-003` |
| 2-8 | 絵文字 (ZWJ シーケンス) と結合文字の表示・キャレット移動が正しい | `PLT-004` |

### プラットフォーム別の難度

| PF | 見込み | 備考 |
|---|---|---|
| Windows | ○ | `winit` が `Ime` イベントを提供する。IMM32/TSF の差異に注意 |
| macOS | ○ | 同上 |
| Linux (X11/Wayland) | △ | fcitx5 / ibus との組み合わせで挙動が分かれる可能性 |
| **Android** | **▲** | `InputConnection` の橋渡しを自前実装する必要がある見込み |
| **iOS** | **▲** | `UITextInput` プロトコルの実装を自前で行う必要がある見込み |

### Go/No-Go

| 条件 | 判定 |
|---|---|
| Windows で 2-2〜2-5 がすべて成立する | **必須** |
| macOS / Linux で同上 | **必須** (macOS は環境確保次第) |
| Android で同上 | **必須** |
| iOS で同上 | 必須。環境未確保なら実現可能性の調査で代替し、ADR に「未検証」と明記する |
| ナレーター / TalkBack が UI を読み上げる | 必須 (`PLT-003`) |

**モバイルの IME が実装不可能と判明した場合、ADR-0001 を破棄して Flutter 案 (ADR-0001 の選択肢 A) へ切り替える。**

### 成果物

- `spike/s2-text-input/`
- ADR-0001 への追記、または **ADR-0005 「ADR-0001 の見直し」** の起票
- `02-architecture.md` のプラットフォーム統合表を確定

## S3. QuickJS 組み込み

### 仮説

> `rquickjs` を全プラットフォーム向けにビルドでき、TypeScript から生成した JS を実行して UITree を変形できる。プラグインを別スレッドに置いてもコストが許容範囲に収まる。

### 検証すること

| # | 内容 | 関連要件 |
|---|---|---|
| 3-1 | `rquickjs` を Windows / Android 向けにビルドする (可能なら macOS / iOS も) | `EXT-030` |
| 3-2 | TypeScript → esbuild → `qjsc` のパイプラインを通す | `EXT-031` |
| 3-3 | ホストが注入した関数のみが到達可能であることを確認する (`globalThis` が最小) | `SEC-010`, `SEC-015` |
| 3-4 | 簡単な UITree (100 ノード程度) をプラグインへ渡し、変形して返す往復のコストを測る | `EXT-032` |
| 3-5 | 無限ループするプラグインを規定時間で強制停止できる | `EXT-051` |
| 3-6 | 例外を送出するプラグインを隔離し、ホストが継続する | `EXT-050` |
| 3-7 | プラグインを再読み込みしても状態が漏れない | `EXT-037` |
| 3-8 | プラグインごとの CPU 時間とメモリを計測できる | `EXT-053` |

### 計測項目

| 指標 | 合格ライン |
|---|---|
| 100 ノードの UITree の往復 (Rust → QuickJS → Rust) | 1ms 未満 |
| プラグイン 1 個あたりのメモリオーバーヘッド | 5MB 未満 |
| プラグイン 10 個を有効化したときの追加フレーム時間 | 2ms 未満 |
| `.qjsc` の読み込み時間 (10KB 程度のプラグイン) | 10ms 未満 |

数値は暫定。実測後に根拠を持って確定する。

### Go/No-Go

| 条件 | 判定 |
|---|---|
| 全対象プラットフォームでビルドが通る | **必須** |
| 3-3 (サンドボックス) が成立する | **必須**。破れるなら設計をやり直す |
| 3-5 (強制停止) が成立する | **必須** |
| 往復コストが合格ラインに収まる | 必須。超える場合は API 設計を差分ベースに寄せて再測定 |

### 成果物

- `spike/s3-plugin-host/`
- ADR-0002 への追記

### S1 の判定

**Windows における Go/No-Go 条件はすべて満たした。**

| 条件 | 結果 |
|---|---|
| 常駐メモリが公式クライアントを下回る | ✅ 69.7MB vs 1,273MB |
| コールドスタートが公式クライアントを下回る | ✅ 332ms |
| 独自タイトルバーが `PLT-021` の挙動を満たす | ✅ 手動確認済 (2026-08-14) |
| スクロールの p99 がリフレッシュ周期に収まる | ⚠️ p99 18.8ms / 周期 16.67ms。約 1% で 1 フレーム落ち |

`NFR-003` のみ未達。原因は毎フレームのインスタンスバッファ全体転送と `ControlFlow::Poll` の疑いがあり、実装では差分更新と `ControlFlow::Wait` に変える。**M1 の実装後に再測定して判定する。**

#### 実行方法

```bash
cd spike/s1-window

# 手動検証: ウィンドウが開くので操作して確認する。Esc で終了し統計を出力
cargo run --release

# 無人ベンチ: 20 秒で自動終了
GUMICORD_BENCH_SECS=20 cargo run --release

# バックエンドを固定して比較
WGPU_BACKEND=gl   GUMICORD_BENCH_SECS=20 cargo run --release
WGPU_BACKEND=dx12 GUMICORD_BENCH_SECS=20 cargo run --release

# 描画負荷を上げる (追加インスタンス数を指定)
GUMICORD_STRESS=20000 GUMICORD_BENCH_SECS=20 cargo run --release
```

> ⚠️ `WGPU_BACKEND=vulkan` は検証機 (Intel HD 520) では**プロセスごとクラッシュする**。既知の挙動。
