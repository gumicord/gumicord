## 1. 実行モデル

### 1.1 隔離の単位

**プラグイン 1 個につき QuickJS の `Runtime` と `Context` を 1 組ずつ持つ。**

```
gumicord-plugin
├─ PluginHost { runtime, context, storage, deadline }   ← plugin A
├─ PluginHost { runtime, context, storage, deadline }   ← plugin B
└─ PluginHost { runtime, context, storage, deadline }   ← plugin C
        ↑ 相互に一切参照できない
```

`Context` を共有すればメモリを節約できるが、**しない**。`EXT-050` (1 つのクラッシュが他に波及しない) と `SEC-014` (ストレージの分離) を実装レベルで自明にするためである。

S3 の実測では、この完全隔離のコストは**プラグイン 1 個あたり 11.3 KB** だった。100 個並べても 10MB 程度である。**隔離のコストを理由に妥協する必要はない。**

### 1.2 スレッド

プラグインの実行はメインスレッドの外で行う ([02-architecture.md](02-architecture.md#スレッドモデル-)) 。

- プラグインは専用スレッド上の全ホストが持ち、メインスレッドとは最新1件のみの郵便受けで渡す
- パッチの適用結果はフレーム境界で取り込む
- 規定時間内に返らなければ**前フレームの結果を再利用**し、当該プラグインに警告を出す
- QuickJS の `Runtime` は `Send` ではないため、プラグインスレッドに固定する

郵便受けは「最新だけ残す」形である。メインスレッドは出来上がった適用結果があれば取り込み、なければ前回のものをそのまま使う。詰まった要求が溜まって雪崩になることはない。

### 1.3 グローバル環境

プラグインから見える `globalThis` には、**ECMAScript の組み込みとホストが明示的に注入したものしか存在しない**。

S3 で実測したプロパティ数は **78 個**。以下はいずれも**存在しない**。

```
require, process, fs, child_process, fetch, XMLHttpRequest,
WebAssembly, importScripts, Deno, Bun
```

> **ケイパビリティモデルは、権限チェックのコードではなく「注入しないこと」で実装される。**
> 宣言していない API は拒否されるのではなく、**存在しない** (`SEC-010`, `SEC-015`)。

`eval` と `Function` は残るが、これらは純粋な JS 評価であり、ホストが注入していない機能には到達できない。ネイティブコードの読み込みや任意コマンド実行の経路にはならない。

ホストが注入するのは `__gumicord_host` ただ 1 つであり、プラグイン作者はこれを直接触らない。`@gumicord/sdk` がラップする。

```
プラグイン → @gumicord/sdk → __gumicord_host → Rust
                   ↑
        この間接層があることでホスト API を変えても吸収できる
```

## 2. パッチ適用の意味論

> **この節は拡張 ABI の一部である。** プラグイン作者が結果を予測できなければ ABI として機能しない。
> 破壊的変更は `EXT-003` の対象となる。

### 2.1 規則

UITree の走査と `ui.patch` の適用は、以下に厳密に従う。

| # | 規則 |
|---|---|
| **P1** | 走査は**ボトムアップ**である。子を先に処理し、自分を後に処理する |
| **P2** | セレクタの照合は、**パッチ適用前の**安定 ID に対して行う |
| **P3** | **パッチの出力に対して再帰しない。** 出力は最終形として扱う |
| **P4** | 同一ノードへの複数のパッチは**登録順**に適用し、後のパッチは前のパッチの出力を受け取る |
| **P5** | **パッチが例外を投げたら、そのノードはパッチ適用前の状態に戻る。** 他のノードにも他のプラグインにも波及しない |
| **P6** | **プラグインは読み込み順に連鎖する。** 後のプラグインは前のプラグインの出力を受け取る |
| **P7** | **パッチは純粋関数でなければならない。** 副作用を持ってはならない |

参照実装:

```js
function applyPatches(node, ctx) {
  // P1: 子を先に処理する
  const current = node.children?.length
    ? { ...node, children: node.children.map((c) => applyPatches(c, ctx)) }
    : node;

  // P2: 照合は「元の」安定 ID で行う
  const list = patches.get(node.id);
  if (!list) return current;

  // P3, P4: 登録順に適用し、出力には再帰しない
  let out = current;
  for (const fn of list) out = fn(out, ctx);
  return out;
}
```

### 2.2 なぜこの規則なのか

**P3 がないと無限再帰する。** S3 で実際に踏んだ。

`ui.wrap` は**元ノードを子として持つ新ノード**を返す。

```js
ui.patch("chat.message.content", (node) =>
  ui.wrap(node, { id: "layout.column" }));
//   ↓ 返り値
// { id: "layout.column", children: [ { id: "chat.message.content", ... } ] }
```

素朴に「自分にパッチ → 結果の子へ再帰」と書くと、この子が再び `chat.message.content` にマッチし、また包まれ、を無限に繰り返して `Maximum call stack size exceeded` で落ちる。

**P1 (ボトムアップ) と P3 (出力に再帰しない) は同じ問題の裏表である。** 子を先に片付けておけば、自分にパッチを当てた後にもう走査するものは残っていない。

**P2 が必要な理由**: パッチが自ノードの ID を変える (`replace` や `wrap`) 場合、適用後の ID で照合すると、どのパッチが当たるかがパッチの実行順に依存してしまう。適用前の ID で照合すれば、**登録されたパッチの集合はツリーの形だけで決まる**。

### 2.3 プラグイン作者が期待してよいこと

- 自分のパッチは、**そのノード 1 つにつき 1 回だけ**呼ばれる
- パッチが受け取るノードの子は、**すでに他のパッチが適用された後**の状態である
- 同じ安定 ID に複数のプラグインがパッチを当てた場合、**読み込み順に連鎖する**
- 自分のパッチが返したノードは、**そのまま使われる**。再び走査されることはない

### 2.4 P5 — 例外の粒度 ✅ (2026-08-14 決定)

**ノード単位で回復し、繰り返すならプラグイン単位で止める。**

```
パッチが例外を投げた
    │
[1] そのノードはパッチ適用前の状態に戻る    ← 他のノードは無傷
    │
[2] プラグイン ID とノード ID つきで記録する
    │
[3] 一定時間内に閾値を超えて例外が続いたら
    │
[4] そのプラグインを無効化し、利用者に通知する (EXT-050)
```

| 段階 | 挙動 |
|---|---|
| 1 回目 | 当該ノードのみ元に戻す。ログに記録 |
| **60 秒以内に 100 回** | プラグインを無効化。理由を記録し、利用者に通知する |

**なぜ両方やるか**:

- **ノード単位だけ**だと、壊れたプラグインが毎フレーム例外を投げ続け、ログを埋め、CPU を食い、しかも利用者は「なんとなく変」としか分からない
- **プラグイン単位だけ**だと、めったに起きない条件分岐の 1 つのバグでプラグイン全体が死ぬ。「たまにアバターが出ないメッセージがある」程度のことで機能を全部失うのは過剰である

閾値の根拠: 壊れたパッチの失敗はフレーム単位で起きる (可視ノード1個でも毎秒60回)。100回/60秒は、壊れたものを2秒以内に止め、散発の失敗には当たらない。実測ではなく構造からの決定であり、運用で外れたら変える。

**ホストが受け取れない出力を返したときも1回と数える。** 未知の安定 ID や壊れた形は、そのフレームのそのプラグインの出力ごと捨てて適用前の部分木を使い、失敗として記録する。部分的に直すと、どの部分が生きているか予測できなくなる。

### 2.5 P6 — プラグイン間の合成 ✅ (2026-08-14 決定)

**プラグインは読み込み順に連鎖する。**

```
ホストの UITree
    │
    ▼ プラグイン A の applyPatches
    │
    ▼ プラグイン B の applyPatches      ← A の出力を受け取る
    │
    ▼ プラグイン C の applyPatches
    │
  テーマ解決へ
```

したがって:

- **B は A が挿入したノードを見る。** A が `primitive.badge` を足せば、B の `primitive.badge` パッチが当たる。プラグインどうしが噛み合う
- **A は B の存在を知らない。** 各プラグインは独立した QuickJS `Context` にいる ([1.1](#11-隔離の単位))
- 読み込み順は利用者が並べ替えられる。依存関係を宣言している場合は解決結果が優先される (`EXT-040`)

> **P3 (パッチの出力に再帰しない) との関係**: P3 は**同一プラグイン内**の規則である。
> プラグイン境界を越えるときは部分木ごと次のプラグインへ渡すため、B は A の出力全体を走査する。
> A が自分の出力を無限に包み続けることはないが、A の出力に B が反応することはある。**これは意図した挙動である。**

### 2.6 P7 — パッチは純粋関数 ✅ (2026-08-14 決定)

仮想化 ([03-uitree.md 7](03-uitree.md#7-仮想化とパッチの関係--2026-08-14-決定)) により、**同じメッセージに対してパッチが何度呼ばれるかは決まっていない**。画面外へ出て戻るたびに呼び直される。

```ts
// ❌ 副作用。スクロールのたびに増え続ける
let count = 0;
ui.patch("chat.message", (node) => { count++; return node; });

// ❌ 副作用。描画のたびにリクエストが飛ぶ
ui.patch("chat.message.content", (node, ctx) => {
  fetch(`https://example.com/log?id=${ctx.data.id}`);
  return node;
});
```

出来事に反応したいときは Gateway イベントのミドルウェア (`EXT-033`, `EXT-034`) を使う。

> **パッチは「見た目を決める」もの、ミドルウェアは「出来事に反応する」もの。**
> この境界は仮想化の都合から生まれたが、結果として設計として健全である。
> 描画のたびに副作用が走る拡張は、そもそも予測できない。

なお `storage.set` はホスト側にあるため副作用だが、**パッチの中から呼ぶべきではない**。設定の保存は設定画面のイベントハンドラで行う。

### 2.7 未確定の論点

| 論点 | 備考 |
|---|---|
| プラグインの適用順をユーザーが並べ替える UI | `EXT-040` (依存解決) と併せて設計する |
| `remove` で消えたノードの子に登録されていたパッチの扱い | P1 により子は先に処理済みなので、消える前に呼ばれる。無駄な計算だが害はない。最適化の余地 |
| P5 の閾値 | 実装後に実測して決める |

## 3. UITree の受け渡し

### 3.1 差分のみを渡す

**UITree 全体をプラグインへ渡してはならない。** 変更のあった部分木のみを渡す。

S3 の実測 (Windows / Intel HD 520 / release):

| 渡すもの | ノード数 | 往復 |
|---|---|---|
| メッセージ一覧全体 | 1601 | **5.242 ms** |
| メッセージ一覧全体 | 401 | 1.354 ms |
| メッセージ一覧全体 | 97 | 0.306 ms |
| **変更のあった 1 メッセージ** | **9** | **0.033 ms** |

1601 ノードを毎フレーム渡すと、VSync 周期 16.67ms の 3 割を 1 プラグインが消費する。10 個有効なら破綻する。

差分のみなら **10 プラグインで 0.33 ms** に収まる。

### 3.2 JSON を使わない

ホスト境界での値の受け渡しは、**ネイティブオブジェクトの構築**で行う。JSON 文字列の往復は使わない。

| ノード数 | ネイティブ | JSON 経由 | 比 |
|---|---|---|---|
| 9 | 0.040 ms | 0.056 ms | 1.4x |
| 97 | 0.306 ms | 0.640 ms | 2.1x |
| 401 | 1.354 ms | 2.428 ms | 1.8x |
| 1601 | 5.242 ms | 9.174 ms | 1.8x |

### 3.3 走査は JS 側で行う

ホストは「この部分木を処理せよ」と渡すだけで、どのノードにどのパッチが当たるかの判定は JS 側で行う。ホスト ↔ JS の往復回数を 1 回に抑えるためである。

### 3.4 ホスト境界のオブジェクトの形 ✅ (M1.1)

行きも帰りもネイティブオブジェクトで、JSON 文字列の往復はしない。

ホスト → JS (1 ノード):

| 項目 | 形 |
|---|---|
| `id` | 安定 ID の文字列 |
| `key` | 読むだけ。snowflake・位置・番号はいずれも文字列 |
| `states` | 立っている状態名の配列 |
| `tint` | データが持ってきた色 (`#RRGGBB`)。無ければ欠ける |
| `content` | 描く内容を素直な値にしたもの。下の表。無いものは欠ける |
| `children` | 子の配列。葉には欠ける |

参照 (`data`) は渡さない。雪崩式の ID であり、JS 側でできることは何もない。本文の読み物としての側面は `ctx.data` が持つ。

`content` の形 (`kind` で区別する):

| `kind` | 中身 |
|---|---|
| `text` | `text` 文字列 |
| `icon` / `image` / `qr` | `name` / `url` / `value` 文字列 |
| `rich` | `spans` 配列。各走りは `text` と `font`・`color` (`{r,g,b,a}`)・`under`・`through`・`hidden`・`revealed`・`link`・`image` |
| `editable` | `text`・`caret`・`selection` (`{start,end}`)・`composing`・`placeholder` |

JS → ホスト (1 ノード):

| 項目 | 扱い |
|---|---|
| `id` | 安定 ID でなければならず、未知の ID の出力はそのプラグインのそのフレームごと捨てる ([2.4](#24-p5--例外の粒度--2026-08-14-決定)) |
| `key`・`states`・`tint` | 読むだけなので持ち帰らない。返ってきたノードは、適用前の同じノード (`id` と `key` が一致) があればその `key`・状態・色・参照を引き継ぎ、なければ空で作る |
| `content` | あるものは上の表で読む。読めなければ出力ごと捨てる (黙って直すと何が描かれるか予測できない) |
| `content` が無い | `props` から描く内容だけを取り出す。下の表 |
| `children` | そのまま受け取る (中身は同じ規則で1個ずつ読む) |

`content` を往復させる理由: `ui.wrap` や `ui.after` は受け取ったノードをそのまま包んで返す。包まれた子の本文が境界で落ちたら、メッセージ本文が消える。SDK の合成子が正しく動くには、返したものがそのまま使われる ([2.3](#23-プラグイン作者が期待してよいこと)) ことが本文にも及ばなければならない。

`props` から描く内容への変換 (`content` が無いときだけ):

| 対象 | `props` | 描く内容 |
|---|---|---|
| `primitive.text`・`primitive.badge`・`primitive.button`・`plugin.*` | `value` / `text` / `label` の順にある最初の文字列 | その文字列 |
| `primitive.icon` | `name` 文字列 | その名の絵 |
| `primitive.image` | `url` 文字列 | その URL の絵 |
| それ以外 | — | 描く内容なし (子は描く) |

`onPress` のような関数は境界を越えられず、黙って落とす。`tone` や `gap` のような見た目の指定はテーマの持ち物なので落とす。どちらも警告は出さない — 正しいプラグインが毎フレーム警告を出すようではログが読めなくなる。

`ctx` は `{ data }` の形でそのまま渡す。中身の解決は渡す側 (アプリ) の仕事であり、無いときは `undefined` である。

## 4. ライフサイクル

### 4.1 再読み込みは Context ごと作り直す

`EXT-037` (再起動なしの有効化・無効化・再読み込み) は、**`Context` を破棄して新しく作る**ことで実現する。同じ `Context` に再評価してはならない。

S3 の実測:

```
同一 Context で 1 回目: storage.launches = "1"
同一 Context で 2 回目: storage.launches = "2"   ← 状態が累積している
同一 Context で 3 回目: storage.launches = "3"

新しい Context で 1 回目: 登録パッチ数 = 2
新しい Context で 2 回目: 登録パッチ数 = 2   ← 漏れなし
新しい Context で 3 回目: 登録パッチ数 = 2
```

`Context` の生成コストは 1 個あたり **0.8 ms** 程度なので、再読み込みの体感には影響しない。

永続ストレージ (`storage`) はホスト側にあるため、意図どおり `Context` の再生成を跨いで残る (`EXT-036`)。

### 4.2 配布形式

`EXT-031` は「TypeScript から生成された JavaScript」と「事前コンパイルされた QuickJS バイトコード」の双方の読み込みを要求する。両対応とするが、**既定の配布形式は minify 済み JavaScript とする。**

S3 の実測:

| | サイズ | 読み込み |
|---|---|---|
| ESM ソース | 2,651 バイト | 0.828 ms |
| minify 済み | 1,556 バイト | — |
| **バイトコード** | **4,460 バイト** (ソースより大きい) | 0.463 ms |

バイトコードは**ソースより大きくなる**。速度差は 1.79 倍だが絶対値では 0.365 ms/個であり、プラグインが数個のうちは体感差がない。100 個を読む段階になれば 36 ms の差になるため、その時点で意味を持つ。

**バイトコードは任意の最適化と位置づけ、既定にはしない。**

### 4.3 開発ワークフロー

```
開発  : TypeScript + @gumicord/sdk (.d.ts で型補完・型検査)
   │
   ├─ gumicord-plugin dev    esbuild --watch + ホットリロード
   │
   └─ gumicord-plugin build  esbuild --minify → plugin.js
                             (任意) qjsc → plugin.qjsc
```

S3 で実測したビルド時間は **12 ms** (2.6 KB のプラグイン)。ウォッチモードとホットリロードを組み合わせれば、ビルドステップが必須であることの不利は実質的に消える。

## 5. 障害の隔離

### 5.1 暴走プラグインの強制停止

`EXT-051` は QuickJS の実行時間フック (`set_interrupt_handler`) で実装する。

S3 の実測: **100 ms の期限に対して 100.2 ms で停止**。精度は十分である。

```rust
runtime.set_interrupt_handler(Some(Box::new(move || {
    match *deadline.borrow() {
        Some(t) => Instant::now() > t,   // true を返すと中断される
        None => false,
    }
})));
```

期限は 2 段である。

| 期限 | 値 | 役割 |
|---|---|---|
| 強制停止 | **100 ms** | 無限ループを殺す。S3 で 100.2 ms に止まることを実測済み |
| フレーム予算 | **8 ms** | 1 フレームぶんの連鎖が超えたら、そのフレームは前回の出力を使い、警告を出す。VSync 周期の半分であり、プラグイン由来の遅れを体感に出さない |

8 ms は初期値であり、実運用で外れたら変える。

### 5.2 例外の隔離

`EXT-050`。プラグインが投げた例外はホスト側で捕捉され、ホストは継続する。S3 で確認済み。

例外を投げたプラグインの扱い (そのノードだけ元に戻すか、プラグイン全体を無効化するか) は [2.4](#24-未確定の論点) の論点。

### 5.3 メモリ上限

プラグインごとに `Runtime::set_memory_limit` と `set_max_stack_size` を設定する。

S3 では 32 MB / 512 KB を設定した。実際のプラグインの使用量が 11.3 KB だったことを考えると、この上限は十分に緩い。具体的な値は実運用のプラグインを見てから決める。

### 5.4 セーフモード

`EXT-052`。全プラグインを読み込まずに起動する経路を用意する。1.1 の隔離設計により、「読み込まない」だけで完全に無効化できる。

起動は `GUMICORD_SAFE_MODE` 環境変数 (`0` 以外なら有効) で切り替える。`GUMICORD_SKIP_LOGIN` と同じ流儀である。

## 7. manifest とケイパビリティ ✅ (M1.1)

### 7.1 manifest

プラグインは 1 ディレクトリ 1 個で、`manifest.json` と本体 (`plugin.js`、またはバイトコード `plugin.qjsc`) からなる。形式は [`plugin-manifest.schema.json`](schema/plugin-manifest.schema.json) が定める。

| 項目 | 意味 |
|---|---|
| `id` | 逆ドメイン (`com.example.translate`)。ディレクトリ名と一致させる |
| `name` | 利用者に見せる名前 |
| `version` | semver |
| `entry` | 本体のファイル名。省略時は `plugin.js` |
| `capabilities` | 使う権限の列。下の一覧にあるものだけ書ける。知らない名前は読み込み失敗 |

### 7.2 ケイパビリティ一覧 (M1.1)

| 権限 | 与えるもの |
|---|---|
| `log` | `log.info` / `warn` / `error` |
| `storage` | `storage.get` / `set` / `remove` |

`ui.exists` とパッチ失敗の報告は権限ではなく配管であり、つねに注入される。前者は安定 ID の有無しか明かさず、後者はホストが無効化の勘定をするためのものである。

宣言していない権限は**存在しない** (`SEC-010`, `SEC-015`)。呼ぼうとすれば `TypeError` になり、パッチの中なら P5 の回復と失敗の勘定が働く。

### 7.3 承認と付与

- 初めて見る manifest の権限は、利用者の許可があるまで**与えない** (`SEC-011`)
- 許可・拒否は `grants.json` (`{id: [権限...]}`) に残す。空列は拒否の記録であり、キーが無い「未確認」とは別である
- 拒否されたプラグインは読み込まない。権限不足のまま動かすと、壊れたパッチの山になり無効化の勘定を無駄に消費するためである
- 許可の取り消しと再確認は設定画面 (`EXT-035`) の仕事であり、M1.1 の範囲外である
