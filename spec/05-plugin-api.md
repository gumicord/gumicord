## 1. 実行モデル

### 1.1 隔離の単位

**プラグイン 1 個につき QuickJS の `Runtime` と `Context` を 1 組ずつ持つ。**

```
gumicord-plugin
├─ PluginHost { runtime, context, storage, deadline }   ← plugin A
├─ PluginHost { runtime, context, storage, deadline }   ← plugin B
└─ PluginHost { runtime, context, storage, deadline }   ← plugin C
        ↑ 相互に一切参照できない
```

`Context` を共有すればメモリを節約できるが、**しない**。`EXT-050` (1 つのクラッシュが他に波及しない) と `SEC-014` (ストレージの分離) を実装レベルで自明にするためである。

S3 の実測では、この完全隔離のコストは**プラグイン 1 個あたり 11.3 KB** だった。100 個並べても 10MB 程度である。**隔離のコストを理由に妥協する必要はない。**

### 1.2 スレッド

プラグインの実行はメインスレッドの外で行う ([02-architecture.md](02-architecture.md#スレッドモデル-)) 。

- パッチの適用結果はフレーム境界で取り込む
- 規定時間内に返らなければ**前フレームの結果を再利用**し、当該プラグインに警告を出す
- QuickJS の `Runtime` は `Send` ではないため、プラグインスレッドに固定する

### 1.3 グローバル環境

プラグインから見える `globalThis` には、**ECMAScript の組み込みとホストが明示的に注入したものしか存在しない**。

S3 で実測したプロパティ数は **78 個**。以下はいずれも**存在しない**。

```
require, process, fs, child_process, fetch, XMLHttpRequest,
WebAssembly, importScripts, Deno, Bun
```

> **ケイパビリティモデルは、権限チェックのコードではなく「注入しないこと」で実装される。**
> 宣言していない API は拒否されるのではなく、**存在しない** (`SEC-010`, `SEC-015`)。

`eval` と `Function` は残るが、これらは純粋な JS 評価であり、ホストが注入していない機能には到達できない。ネイティブコードの読み込みや任意コマンド実行の経路にはならない。

ホストが注入するのは `__gumicord_host` ただ 1 つであり、プラグイン作者はこれを直接触らない。`@gumicord/sdk` がラップする。

```
プラグイン → @gumicord/sdk → __gumicord_host → Rust
                   ↑
        この間接層があることでホスト API を変えても吸収できる
```

## 2. パッチ適用の意味論

> **この節は拡張 ABI の一部である。** プラグイン作者が結果を予測できなければ ABI として機能しない。
> 破壊的変更は `EXT-003` の対象となる。

### 2.1 規則

UITree の走査と `ui.patch` の適用は、以下に厳密に従う。

| # | 規則 |
|---|---|
| **P1** | 走査は**ボトムアップ**である。子を先に処理し、自分を後に処理する |
| **P2** | セレクタの照合は、**パッチ適用前の**安定 ID に対して行う |
| **P3** | **パッチの出力に対して再帰しない。** 出力は最終形として扱う |
| **P4** | 同一ノードへの複数のパッチは**登録順**に適用し、後のパッチは前のパッチの出力を受け取る |

参照実装:

```js
function applyPatches(node, ctx) {
  // P1: 子を先に処理する
  const current = node.children?.length
    ? { ...node, children: node.children.map((c) => applyPatches(c, ctx)) }
    : node;

  // P2: 照合は「元の」安定 ID で行う
  const list = patches.get(node.id);
  if (!list) return current;

  // P3, P4: 登録順に適用し、出力には再帰しない
  let out = current;
  for (const fn of list) out = fn(out, ctx);
  return out;
}
```

### 2.2 なぜこの規則なのか

**P3 がないと無限再帰する。** S3 で実際に踏んだ。

`ui.wrap` は**元ノードを子として持つ新ノード**を返す。

```js
ui.patch("chat.message.content", (node) =>
  ui.wrap(node, { id: "layout.column" }));
//   ↓ 返り値
// { id: "layout.column", children: [ { id: "chat.message.content", ... } ] }
```

素朴に「自分にパッチ → 結果の子へ再帰」と書くと、この子が再び `chat.message.content` にマッチし、また包まれ、を無限に繰り返して `Maximum call stack size exceeded` で落ちる。

**P1 (ボトムアップ) と P3 (出力に再帰しない) は同じ問題の裏表である。** 子を先に片付けておけば、自分にパッチを当てた後にもう走査するものは残っていない。

**P2 が必要な理由**: パッチが自ノードの ID を変える (`replace` や `wrap`) 場合、適用後の ID で照合すると、どのパッチが当たるかがパッチの実行順に依存してしまう。適用前の ID で照合すれば、**登録されたパッチの集合はツリーの形だけで決まる**。

### 2.3 プラグイン作者が期待してよいこと

- 自分のパッチは、**そのノード 1 つにつき 1 回だけ**呼ばれる
- パッチが受け取るノードの子は、**すでに他のパッチが適用された後**の状態である
- 同じ安定 ID に複数のプラグインがパッチを当てた場合、**読み込み順に連鎖する**
- 自分のパッチが返したノードは、**そのまま使われる**。再び走査されることはない

### 2.4 未確定の論点

| 論点 | 備考 |
|---|---|
| プラグインの適用順をユーザーが並べ替えられるべきか | `EXT-040` (依存解決) と関係する |
| パッチが例外を投げたとき、そのノードだけ元に戻すか、プラグイン全体を無効化するか | `EXT-050` の粒度 |
| `remove` で消えたノードの子に登録されていたパッチの扱い | P1 により子は先に処理済みなので、消える前に呼ばれることになる。これでよいか |

## 3. UITree の受け渡し

### 3.1 差分のみを渡す

**UITree 全体をプラグインへ渡してはならない。** 変更のあった部分木のみを渡す。

S3 の実測 (Windows / Intel HD 520 / release):

| 渡すもの | ノード数 | 往復 |
|---|---|---|
| メッセージ一覧全体 | 1601 | **5.242 ms** |
| メッセージ一覧全体 | 401 | 1.354 ms |
| メッセージ一覧全体 | 97 | 0.306 ms |
| **変更のあった 1 メッセージ** | **9** | **0.033 ms** |

1601 ノードを毎フレーム渡すと、VSync 周期 16.67ms の 3 割を 1 プラグインが消費する。10 個有効なら破綻する。

差分のみなら **10 プラグインで 0.33 ms** に収まる。

### 3.2 JSON を使わない

ホスト境界での値の受け渡しは、**ネイティブオブジェクトの構築**で行う。JSON 文字列の往復は使わない。

| ノード数 | ネイティブ | JSON 経由 | 比 |
|---|---|---|---|
| 9 | 0.040 ms | 0.056 ms | 1.4x |
| 97 | 0.306 ms | 0.640 ms | 2.1x |
| 401 | 1.354 ms | 2.428 ms | 1.8x |
| 1601 | 5.242 ms | 9.174 ms | 1.8x |

### 3.3 走査は JS 側で行う

ホストは「この部分木を処理せよ」と渡すだけで、どのノードにどのパッチが当たるかの判定は JS 側で行う。ホスト ↔ JS の往復回数を 1 回に抑えるためである。

## 4. ライフサイクル

### 4.1 再読み込みは Context ごと作り直す

`EXT-037` (再起動なしの有効化・無効化・再読み込み) は、**`Context` を破棄して新しく作る**ことで実現する。同じ `Context` に再評価してはならない。

S3 の実測:

```
同一 Context で 1 回目: storage.launches = "1"
同一 Context で 2 回目: storage.launches = "2"   ← 状態が累積している
同一 Context で 3 回目: storage.launches = "3"

新しい Context で 1 回目: 登録パッチ数 = 2
新しい Context で 2 回目: 登録パッチ数 = 2   ← 漏れなし
新しい Context で 3 回目: 登録パッチ数 = 2
```

`Context` の生成コストは 1 個あたり **0.8 ms** 程度なので、再読み込みの体感には影響しない。

永続ストレージ (`storage`) はホスト側にあるため、意図どおり `Context` の再生成を跨いで残る (`EXT-036`)。

### 4.2 配布形式

`EXT-031` は「TypeScript から生成された JavaScript」と「事前コンパイルされた QuickJS バイトコード」の双方の読み込みを要求する。両対応とするが、**既定の配布形式は minify 済み JavaScript とする。**

S3 の実測:

| | サイズ | 読み込み |
|---|---|---|
| ESM ソース | 2,651 バイト | 0.828 ms |
| minify 済み | 1,556 バイト | — |
| **バイトコード** | **4,460 バイト** (ソースより大きい) | 0.463 ms |

バイトコードは**ソースより大きくなる**。速度差は 1.79 倍だが絶対値では 0.365 ms/個であり、プラグインが数個のうちは体感差がない。100 個を読む段階になれば 36 ms の差になるため、その時点で意味を持つ。

**バイトコードは任意の最適化と位置づけ、既定にはしない。**

### 4.3 開発ワークフロー

```
開発  : TypeScript + @gumicord/sdk (.d.ts で型補完・型検査)
   │
   ├─ gumicord-plugin dev    esbuild --watch + ホットリロード
   │
   └─ gumicord-plugin build  esbuild --minify → plugin.js
                             (任意) qjsc → plugin.qjsc
```

S3 で実測したビルド時間は **12 ms** (2.6 KB のプラグイン)。ウォッチモードとホットリロードを組み合わせれば、ビルドステップが必須であることの不利は実質的に消える。

## 5. 障害の隔離

### 5.1 暴走プラグインの強制停止

`EXT-051` は QuickJS の実行時間フック (`set_interrupt_handler`) で実装する。

S3 の実測: **100 ms の期限に対して 100.2 ms で停止**。精度は十分である。

```rust
runtime.set_interrupt_handler(Some(Box::new(move || {
    match *deadline.borrow() {
        Some(t) => Instant::now() > t,   // true を返すと中断される
        None => false,
    }
})));
```

期限は「パッチ 1 回分」ではなく「1 フレーム分の予算」として設定する。具体的な値は M1 の実装後に実測して決める。

### 5.2 例外の隔離

`EXT-050`。プラグインが投げた例外はホスト側で捕捉され、ホストは継続する。S3 で確認済み。

例外を投げたプラグインの扱い (そのノードだけ元に戻すか、プラグイン全体を無効化するか) は [2.4](#24-未確定の論点) の論点。

### 5.3 メモリ上限

プラグインごとに `Runtime::set_memory_limit` と `set_max_stack_size` を設定する。

S3 では 32 MB / 512 KB を設定した。実際のプラグインの使用量が 11.3 KB だったことを考えると、この上限は十分に緩い。具体的な値は実運用のプラグインを見てから決める。

### 5.4 セーフモード

`EXT-052`。全プラグインを読み込まずに起動する経路を用意する。1.1 の隔離設計により、「読み込まない」だけで完全に無効化できる。
