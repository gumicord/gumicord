## 2. M1 のスコープ

### 2.1 M1 の成否は「拡張が全プラットフォームで同じに動く」で決まる

[00-vision.md の成功判定基準](00-vision.md#成功の判定基準)より:

- [ ] 1 つのテーマ JSON が Windows / Android / iOS で**見た目の差なく**適用される
- [ ] 1 つのプラグインが同 3 環境で**同じ挙動**をする
- [ ] 日本語をインライン変換で入力してメッセージを送信できる (3 環境すべて)
- [ ] 常駐メモリが公式 Electron 版より小さい
- [ ] コールドスタートが公式 Electron 版より速い

**下 2 つは S1 で既に達成の目処が立っている** (69.7MB / 332ms)。**上 3 つが M1 の本体である。**

### 2.2 M1 を 2 つのフェーズに分ける

M1 をそのまま 1 本の作業として進めると、**3 プラットフォーム分の実装が終わるまで何も動かない**期間が長く続く。これは危険である。

したがって M1 を以下の 2 フェーズに分ける。**要件の M1 指定は変えない。**

| フェーズ | 到達点 | 検証されること |
|---|---|---|
| **M1.1 縦に通す** | **Windows のみ**で、ログインからメッセージ送信まで、テーマとプラグインを含めて動く | アーキテクチャ全体が成立すること |
| **M1.2 横に広げる** | Android / iOS へ展開し、同じテーマと同じプラグインが動く | **`EXT-043` — プロジェクトの根本命題** |

> **M1.1 は M1 ではない。** Windows だけで動くクライアントは Gumicord の主張を何も証明していない。
> M1.1 は「M1.2 を安全に始めるための足場」であり、**マイルストーンではなくフェーズゲート**である。

### 2.3 M1 に含めないもの

| 除外するもの | 要件 | 理由 |
|---|---|---|
| リアクション | `FR-029` | M2。メッセージの読み書きが先 |
| メンバー一覧 | `FR-043` | M2 |
| スレッド / フォーラム | `FR-015`, `FR-016` | M2 |
| 通知 | `FR-040`, `FR-041` | M2。5 プラットフォーム分の実装が別途必要 |
| 検索 | `FR-034`, `FR-035` | M2 |
| ファイル添付の**送信** | `FR-030` | M2。表示 (`FR-025`) は M1 |
| コンポーネント (ボタン等) | `FR-032` | M2 |
| スラッシュコマンド | `FR-033` | M2 |
| 複数アカウント | `FR-005` | M2 |
| 音声・映像 | `FR-050`〜 | M3 |
| すりガラス / アニメーション背景 | `EXT-025`, `EXT-026` | M2 |
| プラグインレジストリ | `EXT-044` | M4 |

>
> **`winit` のまま、TSF テキストストアなしで変換候補ウィンドウが出た。**

> この発見は直接には効かない。ただし「テキスト入力層は自前実装が要る」という一般化された
> 前提は弱まったので、**まずプラットフォームの標準経路で足りないかを疑う**こと。

> ### ✅ 本物の Discord として動くようになった (2026-08-22)
>
> QR でログインし、自分のサーバとチャンネルが並び、発言が読め、打った文字が届く。
> **demo の固定データから抜けた。**
>
> 通った経路: 鍵束 → (無ければ QR) → REST でトークン交換 → `GET /users/@me` で検算
> → Gateway 接続 → READY → チャンネルを開くと REST で過去 50 件 → `MESSAGE_CREATE`
> で追いかける。
>
> #### 実機でしか見つからなかったこと
>
> | 症状 | 原因 |
> |---|---|
> | サーバ一覧が空 (誤り無し) | **利用者トークンの READY は名前を `properties` の中に入れる** |
> | 接続が永久に繋ぎ直し続ける | 落ちているギルドの殻に `name` が無く、READY 全体が読めなかった |
> | 2 分放置で「失敗しました」 | **QR の期限切れは取り消しではなく、黙って閉じられる形で来る** |
> | 単体試験だけ panic | rustls の暗号実装が依存の合流結果で 0 個になっていた |
> | 新着も入力中も来ない | **利用者トークンは `op 14` で購読しないと何も送られてこない** |
> | サーバの並びが違う | 並び順は `fixed64` を詰めた形で入っており、可変長整数として読めない |
>
> **どれも実機に繋ぐまで分からなかった。** 型と試験だけでは、相手が何を送ってくるかは
> 決められない。`GUMICORD_LOG=debug` で「READY の形」が鍵の名前だけ出るようにしてある。
>
> #### 「入っていない」と「読み方が違う」は外から見分けが付かない
>
> 並び順で一度間違えた。11 個中 4 個しか拾えず、**しかもその 4 個は別の場所から
> 来ていた**。ここで読み方をいじり始めるのは推測である。
>
> 生のバイト列を 3 通りの形で直接探して、初めて切り分けが付いた:
>
> ```text
>   as_varint=0  as_text=0  as_fixed=11
> ```
>
> **入ってはいた。読み方が違っただけだった。** 数える前に直そうとしていたら、
> 当たるまで試し続けることになっていた。
>
> ⚠️ 記録に出すのは**数だけ**である。識別子そのものを出すと、
> 利用者がどのサーバに入っているかがログに残る。
>
> ### ✅ 再起動しても続きから読める (C5, C6)
>
> **開いた瞬間に前回の画面が出る。** ログインも READY も待たない。
>
> ```text
>   起動 ──▶ SQLite を同期に読む (数 ms) ──▶ 描く
>              │
>              └─▶ 背景でログイン → Gateway → READY で差し替え
> ```
>
> 待たない根拠は S4 の実測である。**READY まで 672〜1120 ms かかり、
> `NFR-001` (500 ms) に入らない。** ログアウトするとキャッシュごと消える
> (`SEC-021`) ので、**残っていること自体が「前回このアカウントで入れていた」
> 証拠**になる。
>
> #### 3 つの出所を 1 つの状態に落とす
>
> | 出所 | 速さ | 正しさ |
> |---|---|---|
> | キャッシュ (SQLite) | すぐ出る | 古い |
> | REST (過去 50 件) | 往復を待つ | 正しい |
> | Gateway | — | 繋いだ後のものだけ |
>
> ⚠️ **REST が先に返ったら、後から来たキャッシュで上書きしない。**
> ⚠️ **REST が失敗しても、キャッシュのぶんは消さない** (`NFR-011`)。
>
> #### ⚠️ キャッシュは暗号化されていない
>
> `SEC-020` は M2 である。**いまの版は、読んだメッセージの本文が平文で
> ディスクに残る。** 仕様が決めた順序だが、使う人が知らないままでよいこと
> ではないので、[`core/store/src/db.rs`](../core/store/src/db.rs) の頭に
> 書いてある。

> ### C3 の 429 検証にモックサーバーは要らなかった
>
> 仕様 [9 章](09-discord-protocol.md#429-からの復帰-nfr-022-)は「429 からの復帰は未検証。M1 の実装時に
> モックサーバーで検証する」としていた。意図的に 429 を起こすには並行リクエストの
> バーストが必要で、`NFR-024` (自動化された連続リクエストを行わない) と衝突するためである。
>
> **レート制限の判断を「眠らない純粋な計算」にしたら、モックすら要らなくなった。**
> `RateLimiter` は時刻を引数で受け、待つべき時間を返すだけである。実際に待つのは
> `RestClient` だけで、そこは薄い。おかげで 429・グローバル制限・バケット共有・
> 壊れたヘッダのすべてを、通信もスリープもなしで試験できる。
>
> **試験しにくいものは、たいてい設計が混ざっている。**

## 4. 依存関係とクリティカルパス

```
B1 workspace
  │
  ├─▶ B2 UITree ─────┬─▶ E1 テーマ ──┬─▶ E2 ホットリロード
  │                  │               └─▶ E3 アセット
  │                  ├─▶ E4 プラグインホスト ─▶ E5 パッチ適用 ─▶ E6 権限 ─▶ E7 SDK
  │                  └─▶ R2 レイアウト ─▶ R1 バッチャ ─┬─▶ R5 画像
  │                                                    └─▶ R6 クリップ/仮想化
  ├─▶ C1 model ─▶ C2 Gateway ─┬─▶ C4 ログイン
  │                            └─▶ C5 Store ─▶ C6 先行描画
  │                     C3 REST ─┘
  │
  └─▶ P1 ウィンドウ ─▶ P2 テキスト入力層 ─────────────────────▶ 日本語入力 ✅
                         │
                         └─ 律速すると見ていたが、TSF は要らなかった (ADR-0006)
```

### 4.1 ~~P2 (TSF) が律速する~~ → **律速しなかった** ✅

当初はこう書いていた。

> **TSF は他のどの作業にも依存しない。** ウィンドウさえあれば着手できる。
> そして**他のどの作業も TSF に依存しない**。
> **したがって P2 は最優先で、かつ並行して進めるべき作業である。**
> 最後に回すと、他が全部できているのに日本語が打てないクライアントが残る。

**この判断は正しかった。ただし理由は想定と違った。**

P2 を先に着手した結果、[TSF テキストストアが不要だったこと](adr/0006-windows-ime-via-winit.md)が分かり、**クリティカルパスそのものが消えた**。
最後に回していたら、M1.1 の他が全部終わったあとで、XL だと思っていたものが実は不要だったと分かるところだった。

> **見積もりが一番大きいものから着手する価値は、実装が終わることだけではない。**
> 「そもそも要らなかった」と早く分かることにもある。

### 4.2 R6 (クリップ / 仮想化) は仕様待ち

仮想化とプラグインのパッチが噛み合わない論点 ([5.1](#51-m1-実装前に決めること)) が未解決である。**R6 に着手する前に決める。**

### 4.3 E5 (パッチ適用) は E1 (テーマ) と順序が決まっている

[02-architecture.md のフレームパイプライン](02-architecture.md#フレームのパイプライン-)より、プラグインの構造介入 → テーマ解決 → プラグインのスタイル介入の順である。実装もこの順序を守る。

### 5.1 M1 実装前に決めること ✅ (2026-08-14 すべて決定)

**コードを書く前に確定させた。** 後から変えると拡張の前提が崩れるため。

| 論点 | 決定 | 場所 |
|---|---|---|
| 仮想化とパッチの整合 | **パッチは生成されたノードにのみ呼ばれ、回数に上限はない。したがって純粋関数でなければならない (V1〜V3, P7)**。全件処理は Gateway ミドルウェアで行う | [03-uitree.md 7](03-uitree.md#7-仮想化とパッチの関係--2026-08-14-決定) |
| プラグインが挿入するノードの ID 空間 | **`primitive.*` / `layout.*` は自由。`plugin.<プラグインID>.*` も可。`app.*` / `chrome.*` / `nav.*` / `chat.*` の生成は禁止** | [03-uitree.md 8](03-uitree.md#8-プラグインが生成するノード--2026-08-14-決定) |
| `data` で公開するフィールドの範囲 | **ノード種別ごとに列挙して固定。生の API ペイロードは公開しない。フィールドも ABI であり削除は破壊的変更** | [03-uitree.md 2.4](03-uitree.md#24-data--ドメインオブジェクトへの参照) |
| パッチ例外の粒度 | **ノード単位で回復し、繰り返すならプラグイン単位で無効化 (P5)** | [05-plugin-api.md 2.4](05-plugin-api.md#24-p5--例外の粒度--2026-08-14-決定) |

これに伴い、パッチ適用の規則は P1〜P4 から **P1〜P7** に増えた。追加分:

| # | 規則 |
|---|---|
| **P5** | 例外を投げたパッチのノードは適用前の状態に戻る。波及しない |
| **P6** | プラグインは読み込み順に連鎖する。後のプラグインは前の出力を受け取る |
| **P7** | パッチは純粋関数でなければならない |

### 6.1 M1.2 の最大リスク

**A2 と I2 が両方 XL で、両方とも未検証である。**

[ADR-0001 の見直し条件](adr/0001-native-rust-renderer.md)より:

> Android または iOS の IME が実装不可能と判明したとき → ADR-0001 ごと再検討する

**緩和策**: **A2 の調査を先行させる。** M1.1 の他の作業と並行できる。

> ⚠️ **Windows で得た教訓を持ち込むこと。** Windows は「自前実装が要る」と結論して XL を積んだが、
> 実際には**プラットフォームの標準経路に正しい値を渡していなかっただけ**だった
> ([ADR-0006](adr/0006-windows-ime-via-winit.md))。
>
> A2 / I2 でも、**まず `android-game-activity` / `UIKit` の標準経路で足りないかを疑う。**
> 「足りない」と結論する前に、渡している値が正しいかを確かめる。

## 8. この文書の扱い

**規模の見積もりは実装が進むにつれて外れる。** 外れたら書き換える。

**実際に外れた。** P2 は XL と見積もっていたが、TSF テキストストアは要らず S で済んだ
([ADR-0006](adr/0006-windows-ime-via-winit.md))。M1.1 の XL は 0 になった。

> 外れ方が「思ったより大きかった」ではなく「**そもそも要らなかった**」だった点が重要である。
> 見積もりを見直すときは、規模だけでなく**その作業が要るのか**を疑う。
