## ルール

### 1. 仕様が先

実装の PR は、対応する要件 ID (`FR-024`, `EXT-032` など) を参照する。参照先がない実装は、まず仕様を書くところから始める。

### 2. 決定は ADR に残す

「なぜこうしたか」「何を却下したか」「どういう条件で見直すか」を書く。特に**却下理由**を書く。書かないと同じ議論を半年後に繰り返す。

ADR は原則として書き換えない。決定を覆すときは新しい ADR を起票し、古い ADR のステータスを `置換 (ADR-XXXX による)` に変更する。

### 3. 拡張 ABI は不可侵

[03-uitree.md](03-uitree.md) の安定 ID は、メジャーバージョン内で破壊的変更をしない (`EXT-003`)。追加のみを許す。

これは技術的な制約ではなく**プロジェクトの約束**である。BetterDiscord のプラグインが壊れ続ける問題を解くことが Gumicord の存在理由であり、この約束を破ると存在理由が消える。

### 4. 推測で決めない

性能・IME・プラットフォーム制約は、実測してから仕様に落とす。数値目標を書くときは根拠となる測定を ADR に紐づける。

暫定の数値には「要スパイク」と明記し、確定した数値と区別する。

### 5. 要件 ID は永久欠番

要件を削除しても ID を再利用しない。廃止した要件は `廃止` としてマークして残す。過去のコミットが参照している ID の意味が変わることを防ぐ。

### 6. コードは英語、仕様は日本語

**2026-08-24 決定。** それまではコメントも識別子も日本語で書いていた。

| | |
|---|---|
| 識別子 (型・関数・変数・定数・モジュール) | **英語のみ。** Rust の命名規則に従う (`snake_case` / `CamelCase` / `SCREAMING_SNAKE_CASE`) |
| コメント | **英語のみ。最小限。** |
| `tracing` のログ | **英語** |
| `cargo xtask` と `sdk/test` が画面に出す文字 | **英語**。開発者しか見ない |
| CI の設定 (`.github/`) と `Cargo.toml` `.cargo/config.toml` の注釈 | **英語** |
| `sdk/` の TypeScript (プラグイン作者が読む) | **英語** |
| `README.md` など `spec/` の外の `.md` | **英語**。外から読まれる |
| コミットメッセージ | **英語** |
| 利用者に見える文字列 | **いまは日本語**。下の「i18n」を見よ |
| 仕様書 (`spec/`) と ADR と [`NEXT.md`](../NEXT.md) | **日本語** |

**日本語のまま残すもの** — どれも「利用者に見える文字列」である:

- `#[error(...)]` の文言。`RestError` はログイン画面に、`GpuError` と
  `SecretError` は起動できなかったときに、そのまま出る
- `AssetRefError` の説明。テーマを書いた人に見せる診断である
- `core/uitree/src/ids.rs` の説明文と、それを `spec/03-uitree.md` の表へ
  書き込む `xtask/src/uitree.rs` の組み立て文字列

#### コメントは「なぜ」だけを書く

**「何をしているか」はコードが言う。** コメントに書くのは、コードから読めない理由だけである。

```rust
// ❌ 何をしているか
// 押された場所を基準の点として渡す
node.with_anchor(Anchor::at(x, y))

// ✅ コードから読めない理由
// The renderer flips and clamps; passing the raw point keeps that decision in one place.
node.with_anchor(Anchor::at(x, y))
```

長さの目安は **1〜2 行**である。それより長い経緯・却下した案・実測値は `spec/` か ADR に置き、コードからは指さない。

#### コメントに番号を書かない

`FR-024` `NFR-005` `EXT-003` といった要件 ID や、`C15` `R6` のような作業番号を**コメントに書かない**。要件とコードの対応は [01-requirements.md](01-requirements.md) が持つ。両側に書くと、片方だけ古くなったときにどちらが正しいか分からなくなる。

**コミットメッセージには書いてよい。** あちらは書いた時点の記録であって、後から古くならない。

#### i18n — 画面の文字はいずれ外へ出す

いま画面に出る文字は**日本語のままコードに埋め込まれている**。

```rust
Item::new(Action::LogOut, "ログアウト")
```

**将来これを外に出して切り替えられるようにする。** そのときに困らないよう、
いまの時点でも次を守る:

- 画面に出る文字は**組み立てず、1 つの文字列として書く**。
  語順は言語で変わるので、`format!("{n} 件")` のような切り貼りは後で直せない
- **ログと画面の文字を同じ定数から取らない。** ログは訳さない
- `RestError` の `Display` のように**画面に出るエラー**は、その旨をコメントに
  1 行残す。訳す対象を後から探せるようにするためである

⚠️ **鍵と辞書の形はまだ決めていない。** 決めたら ADR に残す。

#### なぜ変えたのか

日本語のコメントは書いた本人には速いが、

- **識別子に日本語を使うと `rustfmt` と `clippy` の外に出る。** Rust の規約が想定していない
- コメントに理由を厚く書くと、**同じことが `spec/` とコードの 2 か所に書かれる。** 片方が古くなる
- 要件 ID をコメントに撒くと、要件が動いたときに追う場所が増える

**`spec/` が単一の真実の源である**という 1 行目の原則を、コードの側でも守るということである。
