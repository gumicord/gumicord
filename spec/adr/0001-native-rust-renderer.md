# ADR-0001: UI レンダラを Rust + wgpu で自前実装する

| | |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-14 |
| 関連要件 | `EXT-005`, `EXT-020`, `EXT-043`, `NFR-001`〜`NFR-007`, `PLT-001`〜`PLT-009` |

## 背景

Gumicord の中心要件は「**同一のテーマとプラグインが全プラットフォームで同じ挙動をする**」(`EXT-020`, `EXT-043`) である。

UI レンダラを複数持つと、UITree からプラットフォーム固有ウィジェットへの変換を複数回実装することになり、そこで必ず挙動差が生まれる。差が生まれた瞬間、プラグイン作者は「Android では動くが iOS では崩れる」という分岐を書き始め、BetterDiscord が抱えていた問題を形を変えて再生産する。

**したがってレンダラは単一実装でなければならない。** その上で「本物のネイティブアプリであること」(ビジョンの目標5) を満たす必要がある。

## 決定

**全プラットフォームで共通の Rust + wgpu 製レンダラを自前で実装する。**

UI を描画する層からプラットフォーム統合層まで、Web 技術も既存の UI フレームワークも介さない。

## 検討した選択肢

### A. Flutter (Dart) + Rust core

- ○ UI コード 1 本、AOT ネイティブバイナリ、IME が堅い、実装コストが最も低い
- ○ `flutter_rust_bridge` で Rust core と接続できる
- × **プラグインの自由度が Flutter のウィジェットモデルに制約される。** 描画パスの差し替えやカスタムシェーダの注入といった「無限のカスタム度」は Flutter のレンダリングパイプラインの外側からは行えない
- × Dart ランタイムと QuickJS を両方抱えることになる
- × UI 層が Dart、コアが Rust という二言語構成の恒久的な複雑さ

### B. Compose Multiplatform (Kotlin) + Rust core

- ○ UI コード 1 本
- × **デスクトップが JVM。** 起動時間とメモリで `NFR-001`, `NFR-002` の達成が苦しく、「Electron より軽いネイティブアプリ」という価値提案が弱まる
- × 日本語 IME のインライン変換に既知の弱点があり、`PLT-001`, `PLT-002` のリスクが高い
- × iOS ターゲット (Kotlin/Native + Skia) の成熟度に不安
- × A と同じくプラグインの自由度がフレームワークに制約される

### C. プラットフォームごとにネイティブ (Compose + SwiftUI + 各 OS)

- ○ OS 純正の質感とアクセシビリティは最高
- × **レンダラ実装が 3〜5 個。** `EXT-020`, `EXT-043` (全プラットフォームで同一挙動) の保証が実質不可能
- × 総工数は自前レンダラと大差なく、しかも得られるものが要件と逆行する

### D. Rust + wgpu 自前レンダラ ← **採用**

- ○ **`EXT-020`, `EXT-043` を構造的に保証する。** レンダラが 1 つしかないので挙動差が発生しえない
- ○ **プラグインの自由度に上限がない。** 描画パイプライン全体が自分の手にあるため、ノードの差し替えだけでなくカスタムシェーダの注入やレンダリングパスの追加まで開放できる
- ○ 単一言語 (Rust)。core とレンダラが同一プロセス・同一メモリ空間で、FFI 境界がない
- ○ バイナリとメモリのフットプリントが最小
- × **IME・アクセシビリティ・通知・ファイルピッカー等のプラットフォーム統合を自力で実装する必要がある**
- × 工数が他案の数倍。本プロジェクト最大のリスク

## 決め手

**× のコストは「時間」だが、A/B/C の × は「要件を満たせない」である。**

時間は投入すれば解決するが、フレームワークの制約は投入しても解決しない。Gumicord の存在理由が拡張性である以上、拡張性を犠牲にする選択肢は採れない。

## 想定するクレート構成 (スパイクで検証する)

| 領域 | 第一候補 | 対抗 | 備考 |
|---|---|---|---|
| ウィンドウ・入力 | `winit` | 各 OS を直接叩く | デスクトップ 3 OS + Android + iOS を単一 API で扱える |
| GPU 抽象 | `wgpu` | — | Vulkan / Metal / D3D12 / GLES にマップ |
| 2D 描画 | **自前バッチャ** (角丸矩形・画像・テキストに特化) | `vello`, `skia-safe` | UI の描画プリミティブは限られるため、汎用ベクタエンジンより特化実装が速い |
| テキスト整形 | `cosmic-text` | `parley` + `swash` | 双方向・字形結合・フォントフォールバックを含む (`PLT-004`) |
| アクセシビリティ | `accesskit` | 各 OS を直接叩く | **iOS アダプタの有無は要確認** (`PLT-003`) |
| 非同期 | `tokio` | — | |
| WebSocket | `tokio-tungstenite` | — | Gateway (`NFR-023`) |
| HTTP | `reqwest` | `hyper` 直 | REST (`NFR-021`) |
| ローカル DB | `rusqlite` (FTS5) | `sqlx` | 全文検索 (`FR-035`) と暗号化 (`SEC-020`) |
| JS ランタイム | `rquickjs` | — | [ADR-0002](0002-quickjs-plugin-runtime.md) |

## 結果として引き受けるリスク

| リスク | 影響 | 緩和策 |
|---|---|---|
| IME のインライン変換が 5 プラットフォームすべてで期待通り動かない | `PLT-001`, `PLT-002` が満たせない。**致命的** | スパイク S2 で最優先に検証する |
| `accesskit` が iOS を支援していない | `PLT-003` が iOS で満たせない | スパイク S2 で確認。なければ iOS のみ自前実装するか、要件を降格する |
| 自前 2D バッチャの品質が既存エンジンに届かない | 描画品質の低下 | スパイク S1 で `vello` / `skia-safe` と比較。特化実装が不利なら差し替える |
| モバイルでの GPU 互換性問題 | 一部端末で描画されない | wgpu の GLES バックエンドへのフォールバックを確保する |
| 工数がプロジェクトを頓挫させる | **致命的** | スパイクで実測してから M1 のスコープを再調整する。想定を大きく超える場合、本 ADR を見直す |

## 見直し条件

以下のいずれかが判明した場合、本 ADR を再検討する。

- スパイク S2 で、IME が主要プラットフォームのいずれかで実用水準に達しないと判明したとき
- スパイク完了後の工数見積もりが、当初想定の 3 倍を超えたとき

# スパイク S1 の測定結果 (2026-08-14)

## 測定環境

| | |
|---|---|
| OS | Windows 10 Pro 22H2 (10.0.19045) |
| GPU | **Intel HD Graphics 520** (Skylake, 2015年世代の内蔵 GPU) |
| Rust | 1.97.1 / `winit` 0.30.13 / `wgpu` 30.0.0 |
| ビルド | release, `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, `strip = true` |
| 比較対象 | 公式 Discord デスクトップ版 (実行中、5 プロセス) |

> この GPU は**意図的に低性能な下限基準**として扱う。ここで滑らかに動けば、より新しい環境では余裕がある。

## 発見 1: Vulkan ドライバがプロセスごと落ちる ★重要

**現象**: 既定の設定で release ビルドを起動すると、ウィンドウ生成直後に**セグメンテーション違反でプロセスが即死**する。

**原因**: `wgpu` の既定のバックエンド探索が Vulkan を先に試み、この環境の Intel Vulkan ICD がインスタンス生成中にクラッシュする。Vulkan ローダー (`vulkan-1.dll`) と Intel の ICD はインストールされているため、「Vulkan が無いから使わない」という分岐には入らない。

**得られた教訓**:

> **「対応していないバックエンドは `request_adapter` が `None` を返す」という前提は成り立たない。壊れたドライバはプロセスを道連れにする。**

**帰結 (設計へ反映する)**:

1. バックエンドの探索対象を OS ごとに**明示的に絞る**。Windows では `DX12 | GL` のみを候補とし、Vulkan を探索しない
2. 初回起動時にバックエンドの初期化を**別プロセスで試行**し、成功したものを記録してから本体を起動する (プローブ方式)。ドライバのクラッシュがクライアント本体を落とさないようにする
3. ユーザーがバックエンドを手動で上書きできる設定を用意する

これは自前レンダラ固有の問題ではなく、GPU を直接使うアプリすべてに存在する問題である。Electron が Chromium のブラウザ互換レイヤに肩代わりさせていた部分を、自前で引き受けたということ。

## 発見 2: バックエンド選択がメモリを 16 倍変える ★重要

同一バイナリ・同一シーンで、バックエンドだけを変えた測定。

| バックエンド | WorkingSet | Private | 初フレームまで | GPU 初期化 |
|---|---|---|---|---|
| DX12 | 309.4 MB | 285.7 MB | 845〜982 ms | 723〜842 ms |
| **GL** | **69.7 MB** | **18.1 MB** | **332〜384 ms** | **253〜336 ms** |
| Vulkan | — | — | クラッシュ | クラッシュ |

**メモリの差 285.7MB は、ほぼすべて DX12 バックエンドとドライバに由来する。** 描画内容は同一である。

**これが `vello` を採用しない決定打になった。** `vello` はコンピュートシェーダを前提とするため、Windows では DX12 か Vulkan を強制する。つまり:

- `vello` を選ぶ = この環境で 285MB のメモリと 800ms の起動時間を払うか、クラッシュするか
- 自前バッチャを選ぶ = GL/GLES で動くため 18MB と 330ms で済む

自前バッチャは「既存エンジンに劣るかもしれない妥協」ではなく、**下位互換性という点で戦略的に優位**だった。GLES で動くことは Android の古い端末でも動くことを意味する。

## 発見 3: 自前 SDF バッチャの性能は十分すぎる

角丸矩形を SDF (符号付き距離場) でインスタンス描画する方式で、インスタンス数を変えて測定 (GL バックエンド, 1280x800, VSync 有効)。

| インスタンス数 | 平均フレーム時間 | p99 | 最大 | 実効 fps |
|---|---|---|---|---|
| 112 (実際の UI 1 画面相当) | 16.68 ms | 18.82 ms | 54.95 ms | 60 |
| 1,112 | 16.70 ms | 18.61 ms | 32.28 ms | 60 |
| 5,112 | 16.68 ms | 19.34 ms | 41.09 ms | 60 |
| **20,112** | **16.71 ms** | 21.47 ms | 32.07 ms | **60** |
| 100,112 | 22.90 ms | 29.74 ms | 168.72 ms | 44 |

**実際の Discord 風 UI 1 画面は 100〜800 個程度**の矩形で構成される。2015 年世代の内蔵 GPU で 20,000 個まで 60fps を維持できるということは、**実用上 25〜200 倍の余裕がある**。

汎用ベクタエンジン (`vello` / `skia-safe`) を導入する性能上の理由はない。

> 注: 100,000 インスタンスでの `max = 168.72ms` は、毎フレーム 4.8MB のインスタンスバッファを丸ごと転送していることによるスパイクと見られる。実装では差分更新にするため、この領域には到達しない。

## 発見 4: フットプリント

| 指標 | Gumicord スパイク (GL) | 公式 Discord | 比 |
|---|---|---|---|
| バイナリサイズ | **4.66 MB** | 150〜300 MB 程度 | 約 1/40 |
| WorkingSet | **69.7 MB** | 1,273.0 MB (5 プロセス合計) | **約 1/18** |
| Private メモリ | **18.1 MB** | 1,178.6 MB | 約 1/65 |
| 初フレームまで | **332 ms** | — (未測定) | — |
| スレッド数 | 11 | — | — |

要件との対比:

| 要件 | 目標 | 実測 (GL) | 判定 |
|---|---|---|---|
| `NFR-001` コールドスタート < 1000ms | 1000 ms | 332 ms | ✅ 大幅に達成 |
| `NFR-002` 常駐メモリ < 250MB | 250 MB | 69.7 MB | ✅ 大幅に達成 |
| `NFR-003` スクロール中のフレーム落ちなし | — | p99 18.8ms (周期 16.67ms) | ⚠️ 約 1% のフレームで 1 フレーム落ち |

**ただしこれは空のウィンドウに矩形を並べただけの数字である。** テキスト整形、画像デコード、SQLite、Gateway、QuickJS が乗った後の数字ではない。この 69.7MB は**下限であって見込みではない**。

## 発見 5: `NFR-003` は現状わずかに未達

p99 が 18.82ms で、VSync 周期 16.67ms をわずかに超える。約 1% のフレームで 1 フレーム落ちている。

原因の候補 (未特定):
- `ControlFlow::Poll` による busy loop と VSync 待ちの相互作用
- 毎フレームのインスタンスバッファ全体転送
- Windows のコンポジタ (DWM) との同期

実装では差分更新と `ControlFlow::Wait` + 明示的な再描画要求に変えるため、改善する見込みがある。**M1 の実装後に再測定して判定する。**

## 未検証のまま残った項目

| 項目 | 理由 | 次にやること |
|---|---|---|
| `PLT-021` ウィンドウ操作の等価性 (ドラッグ移動・リサイズ・最大化・スナップ) | 実装済みだが**人間の手による操作確認が必要** | 手動検証 |
| `PLT-022` Windows スナップレイアウト (最大化ボタンのホバー) | `winit` の `with_decorations(false)` では `WM_NCHITTEST` に `HTMAXBUTTON` を返せない | Win32 のウィンドウプロシージャを自前で挿す必要があるか調査 |
| `PLT-009` DPI 変更・ディスプレイ間移動 | 検証機がシングルディスプレイ・スケール 1.0 | 別環境で検証 |
| macOS / Linux / Android / iOS の全項目 | 検証機が Windows のみ | 環境確保が必要 |
| 他 GPU (NVIDIA / AMD / Apple Silicon) でのバックエンド挙動 | 検証機が Intel のみ | 発見 1・2 は GPU 依存のため要追試 |

## 結論

**ADR-0001 の決定を維持する。** 性能面の懸念は解消され、想定より大幅に良い数字が出た。

同時に、**自前レンダラのコストは性能ではなくプラットフォーム統合にある**ことが確認された。S1 で困ったのは描画性能ではなく、GPU ドライバの互換性 (発見 1・2) であり、これは「Electron が肩代わりしていたもの」の一部にすぎない。IME とアクセシビリティを扱う **S2 が本当の関門**である。
