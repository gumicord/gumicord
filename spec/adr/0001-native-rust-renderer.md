# ADR-0001: UI レンダラを Rust + wgpu で自前実装する

| | |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-14 |
| 関連要件 | `EXT-005`, `EXT-020`, `EXT-043`, `NFR-001`〜`NFR-007`, `PLT-001`〜`PLT-009` |

## 背景

Gumicord の中心要件は「**同一のテーマとプラグインが全プラットフォームで同じ挙動をする**」(`EXT-020`, `EXT-043`) である。

UI レンダラを複数持つと、UITree からプラットフォーム固有ウィジェットへの変換を複数回実装することになり、そこで必ず挙動差が生まれる。差が生まれた瞬間、プラグイン作者は「Android では動くが iOS では崩れる」という分岐を書き始め、BetterDiscord が抱えていた問題を形を変えて再生産する。

**したがってレンダラは単一実装でなければならない。** その上で「本物のネイティブアプリであること」(ビジョンの目標5) を満たす必要がある。

## 決定

**全プラットフォームで共通の Rust + wgpu 製レンダラを自前で実装する。**

UI を描画する層からプラットフォーム統合層まで、Web 技術も既存の UI フレームワークも介さない。

## 検討した選択肢

### A. Flutter (Dart) + Rust core

- ○ UI コード 1 本、AOT ネイティブバイナリ、IME が堅い、実装コストが最も低い
- ○ `flutter_rust_bridge` で Rust core と接続できる
- × **プラグインの自由度が Flutter のウィジェットモデルに制約される。** 描画パスの差し替えやカスタムシェーダの注入といった「無限のカスタム度」は Flutter のレンダリングパイプラインの外側からは行えない
- × Dart ランタイムと QuickJS を両方抱えることになる
- × UI 層が Dart、コアが Rust という二言語構成の恒久的な複雑さ

### B. Compose Multiplatform (Kotlin) + Rust core

- ○ UI コード 1 本
- × **デスクトップが JVM。** 起動時間とメモリで `NFR-001`, `NFR-002` の達成が苦しく、「Electron より軽いネイティブアプリ」という価値提案が弱まる
- × 日本語 IME のインライン変換に既知の弱点があり、`PLT-001`, `PLT-002` のリスクが高い
- × iOS ターゲット (Kotlin/Native + Skia) の成熟度に不安
- × A と同じくプラグインの自由度がフレームワークに制約される

### C. プラットフォームごとにネイティブ (Compose + SwiftUI + 各 OS)

- ○ OS 純正の質感とアクセシビリティは最高
- × **レンダラ実装が 3〜5 個。** `EXT-020`, `EXT-043` (全プラットフォームで同一挙動) の保証が実質不可能
- × 総工数は自前レンダラと大差なく、しかも得られるものが要件と逆行する

### D. Rust + wgpu 自前レンダラ ← **採用**

- ○ **`EXT-020`, `EXT-043` を構造的に保証する。** レンダラが 1 つしかないので挙動差が発生しえない
- ○ **プラグインの自由度に上限がない。** 描画パイプライン全体が自分の手にあるため、ノードの差し替えだけでなくカスタムシェーダの注入やレンダリングパスの追加まで開放できる
- ○ 単一言語 (Rust)。core とレンダラが同一プロセス・同一メモリ空間で、FFI 境界がない
- ○ バイナリとメモリのフットプリントが最小
- × **IME・アクセシビリティ・通知・ファイルピッカー等のプラットフォーム統合を自力で実装する必要がある**
- × 工数が他案の数倍。本プロジェクト最大のリスク

## 決め手

**× のコストは「時間」だが、A/B/C の × は「要件を満たせない」である。**

時間は投入すれば解決するが、フレームワークの制約は投入しても解決しない。Gumicord の存在理由が拡張性である以上、拡張性を犠牲にする選択肢は採れない。

## 想定するクレート構成 (スパイクで検証する)

| 領域 | 第一候補 | 対抗 | 備考 |
|---|---|---|---|
| ウィンドウ・入力 | `winit` | 各 OS を直接叩く | デスクトップ 3 OS + Android + iOS を単一 API で扱える |
| GPU 抽象 | `wgpu` | — | Vulkan / Metal / D3D12 / GLES にマップ |
| 2D 描画 | **自前バッチャ** (角丸矩形・画像・テキストに特化) | `vello`, `skia-safe` | UI の描画プリミティブは限られるため、汎用ベクタエンジンより特化実装が速い |
| テキスト整形 | `cosmic-text` | `parley` + `swash` | 双方向・字形結合・フォントフォールバックを含む (`PLT-004`) |
| アクセシビリティ | `accesskit` | 各 OS を直接叩く | **iOS アダプタの有無は要確認** (`PLT-003`) |
| 非同期 | `tokio` | — | |
| WebSocket | `tokio-tungstenite` | — | Gateway (`NFR-023`) |
| HTTP | `reqwest` | `hyper` 直 | REST (`NFR-021`) |
| ローカル DB | `rusqlite` (FTS5) | `sqlx` | 全文検索 (`FR-035`) と暗号化 (`SEC-020`) |
| JS ランタイム | `rquickjs` | — | [ADR-0002](0002-quickjs-plugin-runtime.md) |

## 結果として引き受けるリスク

| リスク | 影響 | 緩和策 |
|---|---|---|
| IME のインライン変換が 5 プラットフォームすべてで期待通り動かない | `PLT-001`, `PLT-002` が満たせない。**致命的** | スパイク S2 で最優先に検証する |
| `accesskit` が iOS を支援していない | `PLT-003` が iOS で満たせない | スパイク S2 で確認。なければ iOS のみ自前実装するか、要件を降格する |
| 自前 2D バッチャの品質が既存エンジンに届かない | 描画品質の低下 | スパイク S1 で `vello` / `skia-safe` と比較。特化実装が不利なら差し替える |
| モバイルでの GPU 互換性問題 | 一部端末で描画されない | wgpu の GLES バックエンドへのフォールバックを確保する |
| 工数がプロジェクトを頓挫させる | **致命的** | スパイクで実測してから M1 のスコープを再調整する。想定を大きく超える場合、本 ADR を見直す |

## 見直し条件

以下のいずれかが判明した場合、本 ADR を再検討する。

- スパイク S2 で、IME が主要プラットフォームのいずれかで実用水準に達しないと判明したとき
- スパイク完了後の工数見積もりが、当初想定の 3 倍を超えたとき
