## 背景

実機で 2 つの症状が出た。

| 症状 | 原因 |
|---|---|
| 指を払っても惰性スクロールが始まらない・すぐ止まる | `FLING_MIN = 120px/s` が Android 標準 (`ViewConfiguration.MINIMUM_FLING_VELOCITY = 50dips/s`) の 2 倍以上で、ゆっくりめのフリックが捨てられる。`FLING_TAU = 0.12s` も短く惰性がすぐ消える |
| スクロールバーのつまみを掴めない | スクロールバーのノードはポインタのホバーがあるときだけ生える (`hovered_scroll`)。タッチにはホバーがないため、モバイルではスクロールバー自体が存在せず、掴みようがない |
| 起動時にログイン画面が一瞬出てからサーバー一覧に切り替わる | 保存トークンからの復帰中 (`Session::Connecting`)、キャッシュがないとログイン画面の骨格が約 1 秒表示され、`Done` でメインへ切り替わる。Discord モバイル版はこの間スプラッシュを出す |

## 決定

### フリングは Android 標準に寄せる

| 定数 | 変更前 | 変更後 | 根拠 |
|---|---|---|---|
| `FLING_MIN` | 120px/s | 50px/s | Android の下限と同値。論理ピクセル≒dip として直読する |
| `FLING_TAU` | 0.12s | 0.25s | 惰性が体感で続く長さ。Discord / Telegram 相当の余韻を狙う |
| `FLING_STOP` | 40px/s | 据え置き | 停止閾値は変えない |
| `FLING_MAX` | 6000px/s | 据え置き | テレポート抑止の上限であり体感に効かない |
| `FLING_DIST_MIN` | 96px | 据え置き | 低速の長い drag の救済は維持する |
| `TAP_SLOP` / `SWIPE_MIN` | 据え置き | — | タップ側を緩めると誤タップが増える。今回の不満は惰性とつまみであり触らない |

### スクロールバーはモバイルで常時出す

- デスクトップは従来どおりホバーがある一覧だけに出す。
- モバイル (`is_mobile()`) ではホバーなしで全一覧に出す。はみ出しがない一覧には出ない (レイアウトが `over <= 0` を置かないため)。
- 指先では幅 10px の軌道が狙えないため、タッチの掴み判定だけ左右に 12px 広げる。マウスの判定は変えない。
- 指を置いたときに軌道の上なら即座に掴み、長押しメニュー・指スクロール・フリング計測は始めない。離したら掴みを放すだけで、タップとしてもスワイプとしても扱わない。

### 起動スプラッシュは UITree 内に出す

- `Session` が起動直後 (`booting`: 初回の確定イベントが未到達) で、キャッシュもログインもない間、`login_screen()` の代わりに `AppScreenLoading` を出す。
- ネイティブの起動画面 (Android SplashScreen API / iOS LaunchScreen) は作らない。UITree 内だけで起動から一貫して描画する。
- 新しい安定 ID は足さない。`app.screen.loading` は ABI に既にあり、中身は既存の `primitive.text` で組む。
- キャッシュがある起動は従来どおり即メイン (C6 の先行描画を崩さない)。

### 却下した選択肢

| | なぜ却下したか |
|---|---|
| タップ側 (`TAP_SLOP` 拡大、`SWIPE_MIN` 縮小) の緩和 | 誤タップ・誤返信が増える。実機計測なしに触る場所ではない |
| タイマーでスクロールバーを消す方式 | イベントループは `Wait` するため消灯タイマーの管理が要る。常時表示で問題が出たらそのとき検討する |
| ネイティブ起動画面の追加 | 殻ごとの実装が 3 つ要る (Android / iOS / デスクトップ)。UITree 内で足りる |
| スプラッシュ用の新安定 ID | `app.screen.loading` が未使用のまま残っている。追加は ABI を広げるだけで要らない |

## 見直し条件

- 実機で惰性が長すぎる・短すぎるとの報告があれば `FLING_TAU` を再調整する。
- つまみの誤掴み (本文スクロールのつもりが掴みになる) が多ければ、掴み余白 12px を縮める。
- 常時スクロールバーが見た目の妨げになるとの報告があれば、操作時表示＋消灯への切替えを検討する (v0.2.0 の UI 棚卸しと一緒に)。

## 追記 (2026-09-24): 実機ログで確定した2件

iPad 実機の `GUMICORD_LOG=debug` から以下が確定した。どちらも受付時間の問題ではなかった。

### 惰性は発動するが端で即死する

初速 2000〜8000px/s で毎回発動していたが、全件 `fling stopped at the bound` で走行 12〜82pxだった。指のドラッグが残り行程を使い切り、惰性に進む先が残らない。対処は受付の緩和ではなく、**上端で履歴読み込み中は惰性を維持する**こと (`hold_fling`、3秒上限付き)。下端 (最新) での停止は正しいため変えない。

### 無効化の後に再同期が来ない

チャンネル切替後に `sync → held=100` の直後に `invalidate → held=0` が来て、その後再同期が来ないことを確認した。以降の差分は範囲外として捨てられ、同一内容の再購読は重複排除で送られず、空の一覧はスクロール末端検出が発火しないため永久に空のままだった。対処は監視中の無効化に対する即時再購読 (`Subscriptions::forget`＋再 `watch`、5秒クールダウン付き)。

## 追記 (2026-09-24 夜): 辺死の大半は微小刻みだった

`at/max` 付き停止ログで、走行 10〜100px・中央付近での死亡が大量に出た。初速は毎回数千px/sあるため、1〜2フレームで死ぬのはホットなループが刻む微小 `dt` の仕業である。各刻みが 0.5px 未満だと「見えない再描画を省く」判定が惰性を殺していた。対処は二つで、どちらも受付の緩和ではない。

- `Fling::step` を `Move / Wait / Spent` の3状態にし、端数を繰り越す。1px 未満は待つだけで死なない
- 離し速度を窓式 (`VelocityTracker`、直近 0.12 秒の傾き) に変える。実機で観測した単発の異常標本 (10万px/s超) が `peak` に残って暴走することを消す。低速の長い drag の救済 (`FLING_DIST_MIN`) は残す

## 追記 (2026-09-26): 公式 desktop の wheel 物理調査 (B0)

`spec/12` の B0 として公式 Discord desktop のスクロール挙動を調べた。
JS の実装を読む代わりに、公開情報の2点で確定した：

- 公式クライアントは Chromium (Electron) で動き、wheel 物理は Chromium
  ネイティブである。`--disable-smooth-scrolling` 起動選択肢が効くことが
  利用者向けに文書化されており、自前の慣性 JS が載っていればこの選択肢は
  効かない
- プラグイン作者向けにも自前スクローラの存在は知られておらず、一覧は
  ネイティブスクロールとして扱われている

よって desktop に自前慣性を寄せる先は無い。`spec/12` の B0 の方針どおり
`is_mobile()` で物理を分離する：desktop は `scroll_by` の直接適用のみ
（wheel 噴きの惰性も touch 解放の惰性も作らない。滑らかさは OS が持つ）、
mobile は `Fling`＋`hold_fling`＋`VelocityTracker` を維持する。

## 追記 (2026-09-23): スプラッシュは文言なし・中央アイコンのみ

起動スプラッシュは「Gumicord」の文字と状態行の2行テキストだったが、
文言なしで画面中央にアプリアイコン (96px) を置くだけに変えた。
理由は見た目の好みである（2026-09-26 訂正：以前の二つの説明は誤りのため削った）。

- 画像は同梱 PNG (`packaging/icons/gumicord.png`) の同期デコードとし、
  CDN 取得には載せない

このために安定 ID を一つ足した (`app.screen.loading.icon`)。当初は
「足さない」と書いたが、汎用の `primitive.image` は大きさを持たず、
テーマのセレクタは完全一致のみ (M1) のため汎用 ID のままでは箱の
大きさを決められない。追加のみの変更であり、破壊的変更には当たらない。

## 追記 (2026-10-02): 一覧を動かした払いは働かない (A4)

`spec/12` の A4 として、iPad 実機で二件が挙がった。同じ原因なので一つに記す。
[03-uitree.md](03-uitree.md) の §3.6 の表にも同じ決めを足した。

- 縦スクロールの最中に、そのスクロールが横はらいと判定されて返信が始まる
- 一員面の内で下へはらくと、一員一覧を動かしていても面が閉じてしまう

### 原因

払いの向きは**指を押した点と離した点の差** (`dx`, `dy`) だけで決めている。
`touch::Tracker::mov` は方向を一切見ずに `Scroll` を返し続けるので、
**同じ一連の指の動きが「スクロール」と「はらい」の二つで報告される**。
どちらが正しいかを比べる受け手が無いまま、応答側ははらいの方を採っていた。

方向の判定に使われるのは差なので、長いスクロールの後に指を押した場所へ引き戻すと
その差は小さくなる。縦へ振った掃引でも差が横的优势になれば横はらいと判定される。
実機ではこれが「縦スクロール途中の誤返信」として現れた。

もう一つ、`Swipe::Point` が報告するのは**押した点**の座標である。一覧はその後に
動いているので、応答側がその座標を今のフレームの配置へ当て直すと、指が実際に
離れた行ではなく別の行を見ることになる。

### 決定

**一覧に載った払いは、スクロールとして確定させ、払いの動作を起こさない。**

払いの実行側が「その払いがどのスクロール先に載っていたか」を受け取り、載っていた場合は
動作しない。載っていなかった場合は従来どおり向きで動作する。受け手側での判定であり、
認識層は画面の形を知らないままでよい。

| 场合 | 従来 | これから |
|---|---|---|
| 一員面の内で下へはらう | 面が閉じる | 一員一覧を動かしていたならスクロールで、閉じたまま。動かしていない場合（把手の掴みしろなど）は従来どおり閉じる |
| 発言の上で左へはらう | 返信が始まる | 一覧を動かしていたなら何もしない。動かしていない場合は従来どおり返信が始まる |

面のはらいの表を書き換えたのは、表が「下への払いで閉じるのは下から出る面」と
書いていたためである。携帯では面そのものが一覧の器である（`panes.members` は
1140px 以上でのみ出る）。この矛盾は `8ce43a4` で棚側に既に解いており、
面の側に追いついていなかっただけであった。

### 却下した案

| 案 | 却下の理由 |
|---|---|
| `Tracker` に当たった hit を持たせ、払いの認識自体を一覧考慮で変える | 払いは一覧以外にも届く。認識層が画面の形を持ち、`render/platform` と app の境界が反転する |
| 受付の時間を緩める (`TAP_SLOP` を大きく、`SWIPE_MIN` を小さく) | 本 ADR の「緩めない」に反る。実測なしに緩めると誤タップが増える |
| 払いの向きを累積の移動量で決める | 累積にすると「一覧の端で指が引き戻す掃引」が横はらいに化ける。差のままだと上の問題が残る |

### 併せて見つかった状態の穴

払いの状態の寿命に穴が二つあり、いずれも誤返信の材料になる。

- `Tracker::release` は `active.take()` を `filter()` より先に評価していた。
  追跡していない id で離すと、追跡中の指ごと消える
- touch phase の `Cancelled` が `message_drive` を消していなかった。
  次に指を置いた瞬間に、前回の払いの起点へ指が繋がり直す

どちらも受付の時間ではない。受け手の状態の寿命の話である。
