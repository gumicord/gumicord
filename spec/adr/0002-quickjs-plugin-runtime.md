# ADR-0002: プラグインランタイムに QuickJS を採用し、開発言語を TypeScript とする

| | |
|---|---|
| ステータス | 承認 |
| 決定日 | 2026-08-14 |
| 関連要件 | `EXT-030`, `EXT-031`, `EXT-043`, `EXT-050`, `EXT-051`, `SEC-010`, `SEC-015` |

## 背景

プラグインは全プラットフォームで同一の挙動をしなければならない (`EXT-043`)。これは実行エンジンが全プラットフォームで同一であることを要求する。

同時に iOS で動作する必要がある。iOS では自プロセス内で実行可能メモリを生成できないため、**JIT コンパイルを行うランタイムは使えない**。App Store の審査を通すかどうかに関わらず、この制約は技術的に存在する。

さらに、`SEC-015` によりプラグインからのネイティブコード実行は禁止されるため、ランタイムはサンドボックスとして機能しなければならない。

## 決定

**プラグインは QuickJS (`rquickjs` 経由) 上で実行する。開発者は TypeScript で書き、ビルド時に JavaScript へ変換する。**

```
開発  : TypeScript + @gumicord/sdk (.d.ts で型補完・型検査)
   │
   ├─ esbuild でバンドル ────────▶ plugin.js       (配布形式 A: 可読)
   │
   └─ qjsc でバイトコード化 ─────▶ plugin.qjsc     (配布形式 B: 起動が速い)
   │
実行  : QuickJS (全プラットフォーム共通)
```

**QuickJS が TypeScript を直接実行するわけではない。** TypeScript は開発体験のためのものであり、実行されるのは常に JavaScript またはそのバイトコードである。これは Vencord と同じ方式であり、既存の Discord プラグイン作者にとって馴染みのあるワークフローになる。

## 検討した選択肢

| 候補 | JIT なしで動くか | 全 PF 同一挙動 | 既存資産 | 判定 |
|---|---|---|---|---|
| **QuickJS** | ○ (インタプリタのみ) | ○ 単一の C 実装 | ○ BD/Vencord 作者がそのまま書ける | **採用** |
| Hermes | ○ (AOT バイトコード) | ○ | △ React Native 寄り | 次点。QuickJS より ES 対応が保守的 |
| V8 / JavaScriptCore | × iOS で JIT 不可 | × PF ごとに版が異なる | ○ | 却下 |
| Lua (`mlua`) | ○ | ○ | × Discord モッダーの資産が活きない | 却下 |
| WASM | ○ (インタプリタ実行) | ○ | × UI 操作の DX が悪い | 将来の追加候補 ([ADR-0002 の見直し条件](#見直し条件)) |
| Dart (Flutter 採用時) | × iOS で動的ロード不可 | × | × | 却下 |

### QuickJS を選んだ理由

1. **単一の C 実装が全プラットフォームで同じバイトコードを同じ意味論で実行する。** `EXT-043` の保証が実装レベルで自明になる
2. **JIT を持たない。** iOS の制約を回避策なしに満たす
3. **BetterDiscord / Vencord の作者がそのまま参入できる。** エコシステムの立ち上がりが本プロジェクトの成否を左右する
4. **サンドボックスが自然。** ホストが明示的に注入した関数以外、プラグインは何にもアクセスできない。ケイパビリティモデル (`SEC-010`) と相性がよい
5. **中断可能。** 実行時間フックにより暴走プラグインを強制停止できる (`EXT-051`)
6. **軽い。** 組み込みバイナリサイズが小さく、複数プラグインを別コンテキストで並走させても負担が小さい

## TypeScript を採用する理由

QuickJS は JS しか実行しないが、開発言語を TypeScript に固定する。

- **UITree の安定 ID を型で表現できる。** `ui.patch("message.header.autor")` のような typo をビルド時に落とせる。UITree が拡張 ABI である以上、型検査の価値が極めて大きい (`EXT-002`)
- ケイパビリティ (`SEC-010`) を型に反映し、manifest で宣言していない API の呼び出しをビルド時に検出できる
- `@gumicord/sdk` の `.d.ts` が実質的な API ドキュメントとして機能する

生の JavaScript での記述も禁止はしない (`EXT-031` は生成された JS を読み込めることを要求している) が、公式ツールチェーンとドキュメントは TypeScript を前提とする。

## 帰結

### 良い方向

- プラグインの配布形式がプラットフォームに依存しない。単一の `.qjsc` がすべての環境で動く
- ホストが注入する API 以外に到達手段がないため、権限モデルの実装が単純になる
- 実行時間・メモリのフックを持つため、プラグインごとのリソース計測 (`EXT-053`) が可能

### 悪い方向 / 引き受けるコスト

- **ビルドステップが必須。** TypeScript を書いて即座に反映されるわけではない → SDK CLI にウォッチモードを実装し、ホットリロード (`EXT-037`) と組み合わせて体感を埋める
- **JIT がないため計算集約的な処理が遅い。** 画像処理や暗号処理のようなプラグインは苦しい → 必要になった時点で WASM サイドモジュールを追加検討する (見直し条件を参照)
- QuickJS の ES 対応は V8 に追随しない。最新の言語機能は使えない場合がある → SDK 側で対応範囲を明記し、esbuild のターゲット設定で吸収する
- Rust ↔ QuickJS の値変換コストがある。UITree のような大きな構造を毎フレーム受け渡すと破綻する → **プラグインには UITree 全体を渡さず、購読したノードのみを渡す差分ベースの API にする** ([05-plugin-api.md](../05-plugin-api.md) で詳細を定義)

## 見直し条件

- 計算集約的なプラグインの需要が実際に現れ、QuickJS の速度が明確なボトルネックになったとき → WASM サイドモジュールの併用を再検討する
- スパイク S3 で `rquickjs` の iOS / Android ビルドに解決不能な問題が見つかったとき → Hermes を評価する

## 発見 1: パッチ適用の意味論を誤ると無限再帰する ★重要

最初に書いたパッチ適用ロジックは以下だった。

```js
// ❌ 誤り
function applyPatches(node, ctx) {
  let current = node;
  for (const fn of patches.get(current.id) ?? []) current = fn(current, ctx);
  if (current.children?.length)
    current = { ...current, children: current.children.map(c => applyPatches(c, ctx)) };
  return current;
}
```

これは `Maximum call stack size exceeded` で落ちる。`ui.wrap` は**元ノードを子として持つ新ノード**を返すため、その子が同じ安定 ID で再びマッチし、また包まれる、を無限に繰り返す。

正しい意味論は以下である。

```js
// ✅ 正しい
function applyPatches(node, ctx) {
  // 1. 子を先に処理する (ボトムアップ)
  const current = node.children?.length
    ? { ...node, children: node.children.map(c => applyPatches(c, ctx)) }
    : node;
  // 2. 照合は「元の」安定 ID で行う
  const list = patches.get(node.id);
  if (!list) return current;
  // 3. 複数パッチは登録順に適用。パッチの出力には再帰しない
  let out = current;
  for (const fn of list) out = fn(out, ctx);
  return out;
}
```

**したがって [05-plugin-api.md](../05-plugin-api.md) は以下を規定しなければならない。**

1. UITree の走査は**ボトムアップ**である (子が先、自分が後)
2. セレクタの照合は**パッチ適用前の**安定 ID に対して行う
3. **パッチの出力に対して再帰しない。** 出力は最終形として扱う
4. 同一ノードへの複数パッチは**登録順**に適用し、後のパッチは前のパッチの出力を受け取る

これは実装の詳細ではなく**拡張 ABI の一部**である。プラグイン作者が結果を予測できなければ ABI として機能しない。

## 発見 2: サンドボックスは期待どおり閉じている

プラグインから見える `globalThis` のプロパティは **78 個**で、すべて ECMAScript の組み込みかホストが明示的に注入したものだった。

```
到達できた「危険な名前」= ["eval", "Function"]
```

`require` / `process` / `fs` / `child_process` / `fetch` / `XMLHttpRequest` / `WebAssembly` / `Deno` / `Bun` はいずれも**存在しない**。

`eval` と `Function` は残るが、これらは純粋な JS 評価であり、**ホストが注入していない機能には到達できない**。ネイティブコードの読み込みや任意コマンドの実行 (`SEC-015`) の経路にはならない。必要なら `Context::base` + 個別の Intrinsic 指定で削ることもできる。

> **ケイパビリティモデルが実装レベルで自明になる**という ADR-0002 の主張は裏付けられた。
> 「宣言していない API は存在しない」を、権限チェックのコードを一行も書かずに実現できている。

## 発見 3: UITree は丸ごと渡してはいけない (差分 API の裏付け)

| 渡し方 | ノード数 | 往復 |
|---|---|---|
| ネイティブ変換 | 9 | 0.040 ms |
| ネイティブ変換 | 97 | 0.306 ms |
| ネイティブ変換 | 401 | 1.354 ms |
| ネイティブ変換 | 1601 | **5.242 ms** |
| **差分のみ (1 メッセージ)** | **9** | **0.033 ms** |

1601 ノード (200 メッセージ相当) を毎フレーム渡すと **5.242ms** かかる。VSync 周期 16.67ms の 3 割を 1 プラグインが食う計算で、10 個有効なら破綻する。

**差分のみを渡せば 0.033ms** であり、10 プラグインでも 0.33ms に収まる。

ADR-0002 の「UITree 全体を渡さず、購読したノードのみを渡す差分ベースの API にする」という帰結は、**実測で正しさが確認された**。

### JSON 経由との比較

| ノード数 | ネイティブ | JSON 経由 | 比 |
|---|---|---|---|
| 9 | 0.040 ms | 0.056 ms | 1.4x |
| 97 | 0.306 ms | 0.640 ms | 2.1x |
| 401 | 1.354 ms | 2.428 ms | 1.8x |
| 1601 | 5.242 ms | 9.174 ms | 1.8x |

ネイティブオブジェクトの構築が JSON 文字列の往復より一貫して 1.4〜2.1 倍速い。**ホスト境界では JSON を使わない。**

## 発見 4: プラグインのフットプリントは極めて小さい

| | |
|---|---|
| 空の Runtime + Context | 98,331 バイト (0.09 MB) |
| プラグイン読込後 | 109,866 バイト (0.10 MB) |
| **プラグイン 1 個の増分** | **11,535 バイト (11.3 KB)** |
| プラグイン 10 個の合計 | 1,098,660 バイト (1.05 MB) |
| プラグイン 10 個の起動時間 | 8.4 ms |

合格ライン (1 個 5MB 未満) に対して **440 倍の余裕**がある。プラグインごとに `Runtime` を分けて完全隔離しても、100 個並べて 10MB 程度である。

**隔離のコストを気にする必要はない。** `EXT-050` (1 つのクラッシュが他に波及しない) を、性能を理由に妥協する必要はない。

## 発見 5: 再読み込みは Context ごと作り直す

同じ `Context` にプラグインを再評価すると、JS 側のモジュール状態が残る。

```
同一 Context で 1 回目: storage.launches = Some("1")
同一 Context で 2 回目: storage.launches = Some("2")   ← 状態が累積している
同一 Context で 3 回目: storage.launches = Some("3")

新しい Context で 1 回目: 登録パッチ数 = 2
新しい Context で 2 回目: 登録パッチ数 = 2   ← 漏れなし
新しい Context で 3 回目: 登録パッチ数 = 2
```

`EXT-037` (再起動なしの再読み込み) は、**`Context` を破棄して作り直す**ことで実現する。コストは 1 個あたり 0.8ms 程度なので問題にならない。

永続ストレージ (`storage`) はホスト側にあるため、意図どおり Context の再生成を跨いで残る。

## 発見 6: バイトコード化の効果は 1.8 倍

| | |
|---|---|
| ESM ソース | 2,651 バイト |
| バイトコード | 4,460 バイト (**ソースより大きい**) |
| バイトコード生成時間 | 0.5 ms |
| ソースからの読み込み | 0.828 ms |
| バイトコードからの読み込み | 0.463 ms |
| **効果** | **1.79 倍速** |

バイトコードは**ソースより大きくなる**。配布サイズを優先するならソース (minify 済み 1,556 バイト) の方が良い。

読み込みが 0.828ms → 0.463ms の差なので、**プラグイン数が少ないうちはバイトコード化の価値は薄い**。100 個のプラグインを読む段階になれば 36ms の差になるため、その時点で意味を持つ。

**帰結**: `EXT-031` は両形式の読み込みを要求しているので両対応のままとするが、**既定の配布形式は minify 済み JS とする**。バイトコードは任意の最適化と位置づける。

## 未検証のまま残った項目

| 項目 | 理由 |
|---|---|
| **Android / iOS での `rquickjs` ビルド** | 環境未確保。3-1 の合格条件「全対象 PF でビルドが通る」は未達 |
| `rquickjs` の `bindgen` フィーチャの要否 | S3 では有効にしてビルドが通ったが、クロスコンパイル時に libclang が要るため、事前生成バインディングで足りるか要確認 |
| 非同期プラグイン (Promise / ジョブキュー) の扱い | スパイクの範囲外 |
| プラグイン間の依存解決 (`EXT-040`) | スパイクの範囲外 |

## 結論

**QuickJS プラグインホストは想定より大幅に良い結果だった。** サンドボックス・隔離・強制停止・メモリのいずれも余裕がある。

S1 / S2 と対照的に、**S3 では「プラットフォームの壁」に一切当たらなかった**。QuickJS が単一の C 実装で自己完結しているためである。これは ADR-0002 が QuickJS を選んだ理由そのものであり、その判断は正しかった。

残るリスクは Android / iOS のビルドのみで、これは S1 / S2 と同じ「環境未確保」の問題である。
