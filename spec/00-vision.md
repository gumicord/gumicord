## 一行で言うと

**「BetterDiscord でできることが、スマホでも、壊れずに、できる」Discord クライアント。**

## 解こうとしている問題

Discord のカスタマイズ文化は BetterDiscord / Vencord が支えてきたが、構造的な限界が3つある。

1. **壊れる。** 公式クライアントの非公開な内部構造 (難読化された React コンポーネント、webpack モジュール ID) にパッチを当てているため、Discord がビルドを更新するたびにプラグインが壊れる。プラグイン作者は永久にメンテナンスを強いられる。
2. **モバイルで動かない。** Electron 前提の仕組みなので、Android / iOS では原理的に同じ拡張が動かない。ユーザーはデスクトップとモバイルで別世界を生きることになる。
3. **重い。** Electron は Chromium ごと抱えるため、常駐アプリとしてのコストが不相応に大きい。

Gumicord はこれを**改造ではなく再実装**で解く。自前クライアントであれば、拡張の受け口を**最初から公開 API として設計**できる。

## 中核となる設計判断

> **拡張は「内部構造へのパッチ」ではなく「公開された安定 ABI への介入」である。**

具体的には、UI を **セマンティック UI ツリー (UITree)** として表現する。UITree のノードは `message.header.author` のような**安定 ID** を持ち、これが拡張の ABI になる。

- **テーマ** = UITree ノードに対するデザイントークンとスタイルルール (JSON)
- **プラグイン** = UITree に対するトランスフォーマ + イベントミドルウェア (TypeScript)

そして UITree を描画するレンダラを**全プラットフォームで単一の Rust 実装**にすることで、「デスクトップでは動くがモバイルでは動かない」という差分を原理的に消す。

詳細は [adr/0004-semantic-uitree-as-extension-abi.md](adr/0004-semantic-uitree-as-extension-abi.md) を参照。

## 目標

1. **拡張の全プラットフォーム互換** — 同一のテーマ / プラグインが Windows / macOS / Linux / Android / iOS で同じ挙動をする
2. **BetterDiscord 級の自由度** — UI ノードの挿入・置換・ラップ・削除、独立ウィンドウ、独自プロトコル、描画パスの差し替えまで許す
3. **壊れない拡張 API** — UITree の安定 ID には破壊的変更をしない。メジャーバージョン内で拡張は動き続ける
4. **公式より良い体験** — 起動時間・メモリ・スクロール追従・日本語 IME・アクセシビリティで公式 Electron 版を上回る
5. **本物のネイティブ** — Web 技術を UI に使わない。AOT コンパイルされた単一バイナリ

## 非目標

明示的に**やらない**こと。ここが曖昧だとスコープが無限に膨らむ。

| 非目標 | 理由 |
|---|---|
| 自動化 / セルフボット機能 | 規約違反の度合いが跳ね上がり、ユーザーの BAN リスクを直接高める。API としても提供しない |
| 公式クライアントの機能の完全網羅 | Nitro 関連の課金導線、ゲーム連携、アクティビティなどは初期スコープ外 |
| Discord API の代替サーバー実装 | クライアントのみを作る |
| Web 版 / ブラウザ拡張 | ネイティブに集中する。将来検討はするが仕様には含めない |
| プラグインによる任意ネイティブコード実行 | サンドボックスを破壊し、マルウェア配布経路になる。QuickJS の外には出さない |
| 難読化・検出回避 | 公式クライアントと同等の通信挙動を「隠すため」ではなく「行儀よくするため」に採る。回避技術は実装しない |

## リスクと前提

### 利用規約

Discord の利用規約はサードパーティクライアントの使用を認めていない。**Gumicord を使うとアカウントが停止される可能性がある。**これは設計で消せるリスクではない。

前提として受け入れた上で、以下を設計目標とする。

- 公式クライアントと同等のレート制限遵守、リトライ、バックオフを実装する (要件 `NFR-021`)
- 自動化機能を提供しない (非目標)
- 初回起動時にリスクをユーザーへ明示する (要件 `SEC-004`)

これは「回避」ではなく「サーバーに余計な負荷をかけない実装をする」という方針である。

### iOS の配布

App Store の審査を通る見込みは低い。サイドロード (AltStore / TrollStore / 開発者証明書) を現実的な配布経路として想定する。
ただし**技術的な制約は App Store 準拠で設計する** — 具体的には JIT を使わない。これによりプラグインランタイムの選択肢が QuickJS に絞られる ([adr/0002](adr/0002-quickjs-plugin-runtime.md))。

### プラグインのセキュリティ

拡張の自由度を最大化することは、悪意ある拡張の被害も最大化することを意味する。**自由度とセキュリティのトレードオフはケイパビリティベースの権限モデルで解く** — 何ができるかを manifest で宣言させ、ユーザーが承認する ([spec/05-plugin-api.md](05-plugin-api.md))。「無限の自由度」は「無審査で何でも実行できる」という意味ではない。

### 工数

Rust 自前レンダラは、IME・アクセシビリティ・通知・ファイルピッカーなどのプラットフォーム統合を自力で実装することを意味する。これは他案の数倍の工数であり、**このプロジェクト最大のリスク**である ([adr/0001](adr/0001-native-rust-renderer.md))。
スパイクフェーズはこのリスクを早期に測定するために存在する ([08-spike-plan.md](08-spike-plan.md))。

## 成功の判定基準

M1 (最初のマイルストーン) 時点で、以下がすべて満たされていること。

- [ ] 1つのテーマ JSON が Windows / Android / iOS で**見た目の差なく**適用される
- [ ] 1つのプラグイン (`.qjsc`) が同3環境で**同じ挙動**をする
- [ ] 日本語をインライン変換で入力してメッセージを送信できる (3環境すべて)
- [ ] 常駐メモリが公式 Electron 版より小さい (実測で比較)
- [ ] コールドスタートが公式 Electron 版より速い (実測で比較)
