## 1. 責務

`gumicord-render` は **UITree を受け取り、GPU の描画コマンドを出す**ところまでを担う。

| 担う | 担わない |
|---|---|
| レイアウト計算 | UITree の構築 (`gumicord-uitree`) |
| 描画コマンドの生成とバッチング | テーマの解決 (`gumicord-theme`) |
| テキスト整形とグリフのラスタライズ | プラグインの実行 (`gumicord-plugin`) |
| 画像のデコードとテクスチャ管理 | ウィンドウ・入力・IME (`gumicord-platform`) |
| GPU バックエンドの選択 | ネットワーク (`gumicord-gateway` / `-rest`) |

**プラットフォーム固有のコードを一切含まない。** OS に触る必要が生じたら、それは `gumicord-platform` の仕事である。

## 2. 描画パイプライン

```
UITree (スタイル解決済み)
    │
[1] レイアウト        制約を上から、サイズを下から。1 パス
    │
[2] 描画コマンド生成   ノードを 3 種類のプリミティブへ分解
    │                   ├─ 角丸矩形 (SDF)
    │                   ├─ テクスチャ付きクアッド (画像・グリフ)
    │                   └─ クリップ矩形
    │
[3] バッチング        パイプラインとテクスチャが同じものをまとめる
    │
[4] GPU 送出          インスタンスバッファを書き込み、draw を発行
    │
[5] present
```

### 2.1 プリミティブは 3 種類しかない

UI の描画は「角丸矩形」「テクスチャ付きクアッド」「クリップ」に集約される。
S1 でこの前提を検証した ([ADR-0001 発見 3](adr/0001-native-rust-renderer.md#発見-3-自前-sdf-バッチャの性能は十分すぎる))。

| プリミティブ | 用途 |
|---|---|
| 角丸矩形 | 背景・枠線・区切り線・キャレット・選択範囲・下線 |
| テクスチャ付きクアッド | 画像・グリフ・絵文字・アバター |
| クリップ矩形 | スクロール領域・オーバーフローの切り取り |

汎用のパスやベジェ曲線は**持たない**。必要になったらアイコンをテクスチャとして持つ。

## 3. 座標系と DPI (`PLT-009`)

| | |
|---|---|
| 原点 | 左上 |
| 単位 (仕様・テーマ) | **論理ピクセル** |
| 単位 (描画) | **物理ピクセル** |
| 変換 | 論理 × `scale_factor` = 物理 |

**テーマと UITree はすべて論理ピクセルで表現する** ([04-theme.md 3.3](04-theme.md#33-値の型))。物理ピクセルへの変換はレイアウトの最後に一度だけ行う。

`ScaleFactorChanged` を受けたらレイアウトを再計算し、グリフアトラスを破棄して作り直す (グリフは物理ピクセルでラスタライズされているため)。

### 3.1 スナップ

角丸矩形の辺と 1px の区切り線は、**物理ピクセルグリッドに丸める**。丸めないと 1px の線が 2px にぼやける。

テキストのベースラインは丸めるが、字送りは丸めない (整形結果が壊れるため)。

## 4. 色空間

| | |
|---|---|
| サーフェスの形式 | sRGB (`is_srgb()` が真のものを選ぶ) |
| テーマの色 | sRGB |
| ブレンド | `BlendState::ALPHA_BLENDING` (ストレートアルファ) |

**`EXT-020` (全プラットフォームで同一の描画結果) はここに依存する。** サーフェス形式が環境によって変わると、同じ `#7c6cf0` が違う色に見える。sRGB のサーフェスが取れない環境では、シェーダ側で変換して**出力を揃える**。

## 5. 角丸矩形 (S1 で実証済み)

符号付き距離場 (SDF) によるインスタンス描画。頂点バッファを持たず、`vertex_index` から三角形ストリップの 4 頂点を生成する。

```wgsl
fn sd_round_box(p: vec2<f32>, b: vec2<f32>, r: f32) -> f32 {
    let q = abs(p) - b + vec2<f32>(r, r);
    return length(max(q, vec2<f32>(0.0, 0.0))) + min(max(q.x, q.y), 0.0) - r;
}

// 画面空間の微分でアンチエイリアス幅を決める。DPI に自動追従する。
let aa = max(fwidth(d), 0.0001);
let alpha = 1.0 - smoothstep(-aa, aa, d);
```

**アンチエイリアスに MSAA を使わない。** `fwidth` による解析的な AA で足りる上、DPI スケールに自動で追従する。

### 5.1 実測された性能 (S1)

Intel HD Graphics 520 / 1280x800 / VSync 有効。

| インスタンス数 | 平均 | p99 | 実効 fps |
|---|---|---|---|
| 112 (UI 1 画面相当) | 16.68 ms | 18.82 ms | 60 |
| 5,112 | 16.68 ms | 19.34 ms | 60 |
| **20,112** | **16.71 ms** | 21.47 ms | **60** |
| 100,112 | 22.90 ms | 29.74 ms | 44 |

**実用上 25〜200 倍の余裕がある。**

### 5.2 インスタンスの形式

| フィールド | 型 | バイト |
|---|---|---|
| `rect` | `vec4<f32>` (x, y, w, h) | 16 |
| `color` | `vec4<f32>` | 16 |
| `params` | `vec2<f32>` (radius, border) (+ padding) | 16 |
| 合計 | | **48** |

角ごとに異なる半径が必要になった時点で `radius` を `vec4` に拡張する (M2)。

### 5.3 枠線はリングとして描く

`border > 0` のインスタンスは、塗り潰しではなく**輪だけ**を塗る。

```wgsl
var alpha = 1.0 - smoothstep(-aa, aa, d);
if (in.border > 0.0) {
    let inner = 1.0 - smoothstep(-aa, aa, d + in.border);   // 内側の縁は d == -border
    alpha = max(alpha - inner, 0.0);
}
```

**「一回り大きい矩形を敷いて、内側に背景を重ねる」方式は採れない。** 背景が半透明のとき枠線の色が中まで透けるためである。`midnight` の `chat.message` は `when.state = mentioned` で背景 `#7c6cf01a` (透明度 10%) と枠線 `#7c6cf0` を同時に指定しており、この方式ではメッセージ全体が不透明の紫になる。

`EXT-024` (すべてのノードで正しいアルファ合成) は、枠線についてもこれを要求する。

合成順は **背景 → 画像 → tint → 枠線**である。枠線は最後に、背景の上へ重ねる。

## 6. テキスト (S2 で実証済み)

```
cosmic-text で整形 (shaping / bidi / フォントフォールバック)
    │
swash でグリフをラスタライズ
    │
RGBA8 アトラス (2048x2048, 棚詰め) へアップロード
    │
テクスチャ付きクアッドとして描画
```

### 6.1 アトラスが RGBA8 である理由

**カラー絵文字のため。** マスクグリフは `(255, 255, 255, alpha)` として格納し、シェーダ側で色を掛ける。カラーグリフはテクスチャの色をそのまま使う。

```wgsl
if (in.flags > 0.5) {
    return vec4<f32>(tex.rgb, tex.a * in.color.a);   // カラー絵文字
}
return vec4<f32>(in.color.rgb, in.color.a * tex.a);  // マスクグリフ
```

S2 で 👨‍👩‍👧‍👦 (ZWJ 家族シーケンス) がカラーで描画されることを確認した。

### 6.2 アトラスの管理

S2 の実装は棚詰め (shelf packing) のみで、**溢れたら諦めていた**。実装では以下が必要。

| 課題 | 方針 |
|---|---|
| アトラスの溢れ (文字) | ✅ **複数ページ化** (9.7)。ページごとに束を分ける |
| アトラスの溢れ (絵) | ✅ **まとめて忘れて詰め直す** (9.6)。棚詰めは途中の 1 枚を空けられない |
| 不要グリフの回収 | フレーム単位の LRU。数フレーム使われなかったページを再利用 |
| DPI 変更 | 全ページ破棄して作り直す |
| フォント変更 (テーマ再読み込み) | 同上 |

### 6.2.1 アイコンは字ではなくテクスチャである

タイトルバーの最小化・最大化・閉じるを `−` `□` `✕` の**文字**で描くと、太さも大きさも書体任せになり、ピクセルグリッドにも乗らない。3 つ並べたときに揃わないのは、字としては正しくてもアイコンとしては誤りである。

Windows には Segoe Fluent Icons があるが、それを使うと Windows でしか同じ見た目にならず `EXT-020` と正面から衝突する。

したがってアイコンは**単位正方形 (0.0〜1.0) 上の折れ線**として定義し、描画に要る物理ピクセルの大きさが決まった時点で CPU でラスタライズして、グリフと同じアトラスへ載せる。

| | |
|---|---|
| 定義 | 折れ線の集まりと線の太さ。`gumicord-render` の `icon` モジュール |
| ラスタライズ | 点と線分の距離から 1px の傾斜でアンチエイリアス |
| アトラス | グリフと**同じ 1 枚**。分けるとパイプラインの切り替えが増える |
| 位置 | 整数ピクセルへ合わせる。半端な位置に置くと輪郭がぼやける |
| 大きさ | テーマの `font.size` を基準にする。行の中に混ぜたときに揃う |

SVG を読まないのは、パーサとパス塗りつぶしを持ち込む必要があるからである。いま要るのは線分の集まりだけで、それは点と線分の距離で書ける。**同じ大きさなら全プラットフォームで 1 ビットも違わない** (`EXT-020`)。

UITree 側は `Content::Icon(名前)` で指す。**知らない名前は誤りではない** — 新しいクライアント向けに書かれたプラグインを古いクライアントで動かすと起こりうるので、描かずに進む。

### 6.3 フォント列挙は起動パスに置かない

S2 の実測: `FontSystem::new()` に**初回 360.4 ms**、2 回目以降 27.9〜54.0 ms。

`NFR-001` (コールドスタート 500ms) の予算に対して初回の 360ms は致命的である。

**方針**: 起動時はクライアント同梱フォントのみでレイアウトを開始し、システムフォントの列挙はバックグラウンドスレッドで行う。列挙結果はディスクにキャッシュする。列挙完了後、フォントフォールバックが必要なテキストのみ再整形する。

### 6.4 同梱フォント

本文フォントは**クライアントに同梱する**。理由は 3 つある。

| | |
|---|---|
| `EXT-020` | システムフォント任せだと環境ごとに書体が変わる。「全プラットフォームで同一の描画結果」を主張できない |
| `NFR-001` | [6.3](#63-フォント列挙は起動パスに置かない) を実現するには、まず同梱フォントだけで整形を始められる必要がある |
| 見た目 | OS の既定 sans-serif は UI 用に設計されていない |

現在同梱しているのは **Inter (SIL OFL 1.1)** の可変フォント 1 本である。出処とライセンスは [`assets/fonts/README.md`](../assets/fonts/README.md)。

可変フォントを 1 本にしているのは、cosmic-text がラスタライズ時に `wght` 軸を設定するためである。重さごとに静的インスタンスを持つと、テーマが新しい重さを使い始めるたびにファイルが増える。

#### CJK は同梱していない

日本語はシステムフォントへのフォールバックで描いている。Noto Sans JP の可変フォントは約 5.7MB あり、バイナリが倍以上になる。`EXT-020` の観点では同梱すべきだが、バイナリサイズとの取引である。**決めたら ADR に残す。**

### 6.5 Han 統合 — 日本語が中国語の書体で描かれる問題

**漢字は Han 統合により、同じ符号位置でも言語によって字形が違う。** どの書体を選ぶかは locale で決まる。

cosmic-text 0.19 の判定は locale の**完全一致**であり、`"ja"` / `"ko"` / `"zh-HK"` / `"zh-TW"` / それ以外 の 5 択しかない。Windows が返す `"ja-JP"` はどれにも当たらず、既定の `Microsoft YaHei UI` (簡体字中国語) に落ちる。

対処は 2 段構えである。

1. **locale を正規化する。** 地域まで見る必要があるのは中国語だけなので、それ以外は主言語タグへ切り詰める (`ja-JP` → `ja`、`ja_JP.UTF-8` → `ja`)
2. **フォールバック一覧を自前で持つ。** cosmic-text の Windows 用の表は日本語に `Yu Gothic` 1 つしか持たない。UI 用の `Yu Gothic UI` を先に試し、macOS / Linux / Android の名前も同じ順序で並べる

> ⚠️ **中国語・韓国語の利用者から字形を横取りしてはならない。** locale が `zh` / `ko` で始まるときはプラットフォームの判断に任せる。

これを完全に解くには [6.4](#64-同梱フォント) の CJK 同梱が要る。同梱すれば locale に関係なく同じ字形になる。

### 6.6 飾りの混じった文字 (`FR-021`)

Markdown の本文は、1 つの段落の中で太字・斜体・下線・打ち消し・色が入れ替わる。

> ⚠️ **飾りごとにノードを作って横に並べてはいけない。**
>
> 並べたノードは**それぞれが独立して折り返す**。`これは **とても長い** 文章` は「`これは `」「`とても長い`」「` 文章`」の 3 つが別々に折り返し先を決めることになり、行末が合わない。行の折り返しは、混じったまま**一度に整形して**はじめて正しく決まる。

したがって飾りは中身側に持たせ、ノードは 1 つのままにする。`Content::Rich(Vec<Span>)` である。

| `Span` が持つもの | |
|---|---|
| `text` | この飾りが掛かっている文字 |
| `font` | 書体。`None` ならノードの書体を引き継ぐ |
| `color` | 文字色。`None` ならノードの色 |
| `line` | 下線 / 打ち消し。**重ねられる** |
| `hidden` | スポイラー。**場所は空けたまま隠す** |
| `revealed` | 開かれた隠し走り。`hidden` を**消さずに**重ねる — 消すとスポイラー由来の走りが地の文と区別できなくなり、個別に開けなくなるため。`hidden` かつ `revealed` でないのが「まだ見えない」 |
| `link` | 押したときの行き先 (`FR-036`)。`None` はどんなに色が付いていても押せない |

> ⚠️ **`Span` に入るのはテーマが決めた結果である。** 「太字である」ではなく「太さ 700 である」が入る。太字を何で表すかはテーマの領分 ([04-theme.md](04-theme.md)) であり、ここまで来た時点でその判断は済んでいる。意味 (`Deco::BOLD` のような) をここへ持ち込むと、**レンダラが太字の見た目を決めることになる**。

整形は cosmic-text の `set_rich_text` に流す。走りごとに `Attrs::metadata` で番号を持たせ、出てきたグリフの `metadata` から「この字はどの走りから来たか」を引く。

> ⚠️ **番号を持たせずに、整形後にバイト位置から数え直さないこと。** 走りが空文字列を含むと数え直しは合わない。

下線・打ち消し・スポイラーの塗りは、走りごとの矩形 (`Shaped::runs`) で行う。**この矩形は行ごとに切れている** — 折り返した走りを 1 つの矩形で塗ると行間まで塗り、本文が読めなくなる (選択範囲の `range_rects` と同じ理由)。

スポイラーは**字を積まずに**塗る。上から塗るだけでは、角丸の外や半透明のところから中身が漏れる。

#### リンクの当たり判定 (`FR-036`)

リンクはノードになれない ([9 章 未確定の論点](03-uitree.md#9-未確定の論点) の決着どおり) ので、当たり判定も整形から取り直す。`Shaped::runs` — 下線とスポイラーの塗りに使うのと同じ走りごとの矩形 — を押した位置で引けば、押されたのがどの走りか分かる。

| 規則 | 理由 |
|---|---|
| 矩形は行ごとに分けて持つ | 折り返した URL は 2 つの矩形になる。どちらも押せる |
| まだ見えない走り (`hidden` かつ `revealed` でない) は出さない | スポイラーの下はまだ知らないことである。開けば出る |
| 前面のものが勝つ | 描画順の逆に引く。ヒットテストと同じ |
| 行き先を OS へ渡すのはプラットフォーム層だけ | レンダラは URL を持つだけで開かない。http/https 以外は層の中で拒否する |

#### スポイラーの当たり判定

リンクと同じ仕掛けで、隠れた走りを押した位置で引く。

| 規則 | 理由 |
|---|---|
| 対象は `hidden` の走り。**開いた後も出す** | もう 1 度押して閉じ直せるから |
| 走りの名前は `(メッセージ id, 走りの番号)` | 矩形は描き直しのたびに変わるが、この組は変わらない |
| 番号は、そのメッセージの空でないスポイラー走りを**描画順に**数えたもの | 作る側 (`Ink`) と描く側が別々に同じ数え方をする。順番表を受け渡しはしない — 押された位置から逆に引く以上、渡しようがない |
| 折り返した走りは番号 1 つ、矩形は行ごと | 行ごとに番号を作ると 1 行だけ開いて残りが閉じたままになる |
| まだ見えない走りからはリンクを出さない | 中身を知られたくて隠しているのである。開いた後はリンクのほうが押しに勝つ |

#### 走りの切れ目は行に影響しない

同じ書体で 2 つに割った走りは、割らずに 1 つで書いたものと **1 ピクセルも違わない**。ここが崩れると、飾りを付けた途端に行末がずれる。試験で押さえてある (`text.rs` の `走りの切れ目は行に影響しない`)。

## 7. 画像 (`EXT-021`〜`EXT-024`, `EXT-027`)

**背景画像のために新設する経路。** S2 のグリフアトラスと同じテクスチャ付きクアッドの機構を使うが、**アトラスに詰めず個別のテクスチャとして持つ**。背景画像は大きく、枚数が少ないため。

### 7.1 読み込み

```
アセット参照 (相対パス / data: / https:)
    │
[検証]  パスがテーマディレクトリ内か / ホストが承認済みか (SEC-022, SEC-023)
    │
[取得]  ファイル読み込み or HTTP GET (認証情報なし, SEC-024)
    │
[デコード]  PNG / JPEG / WebP / AVIF     ← ワーカースレッド
    │
[前処理]  blur (EXT-023) をここで一度だけ適用
    │
[アップロード]  テクスチャ + ミップマップ生成
    │
[キャッシュ]  ローカルに保存 (SEC-025)
```

**デコードと blur はメインスレッドの外で行う。** 完了までは `background.color` を描画し、完了したフレームから画像に切り替える。

読み込みに失敗したら `background.color` にフォールバックし、設定画面に警告を出す (`EXT-027`)。**テーマ全体を無効化しない。**

### 7.2 `blur` は読み込み時に一度だけ (`EXT-023`)

デコード後の画像に対して 1 回だけガウシアンぼかしを適用し、**結果をテクスチャとしてキャッシュする**。毎フレームぼかさない。

半径が変わるのはテーマ再読み込み時のみなので、これで足りる。

> `EXT-025` (背後をぼかすすりガラス) は**別の機構**であり M2。あちらは背後の内容が毎フレーム変わるため、
> フレームバッファのコピー + ダウンサンプル + 二段ぼかしが要る。Intel HD 520 での実測を経てから設計する。

### 7.3 `fit` の実装

UV 矩形の計算で表現する。頂点位置は常にノードの矩形いっぱいで、**サンプリング範囲だけを変える**。

| `fit` | UV の決め方 |
|---|---|
| `cover` | アスペクト比を保ち、短辺を合わせて長辺を `position` で切り取る |
| `contain` | アスペクト比を保ち、長辺を合わせて余白を `background.color` で埋める |
| `stretch` | UV を `[0,1]` 固定。アスペクト比を無視する |
| `tile` | UV を `ノードサイズ / 画像サイズ` まで伸ばし、サンプラを `Repeat` にする |
| `none` | 原寸。`position` で寄せる |

`cover` と `tile` では**ミップマップが必須**である。縮小時にエイリアシングが出る。

### 7.4 合成順序 (`EXT-022`)

1 ノードの背景は最大 3 回の描画になる。

```
[1] color   角丸矩形として描画
[2] image   テクスチャ付きクアッド (opacity 適用)
[3] tint    角丸矩形として描画
```

いずれも指定がなければ省略する。`image` と `tint` はノードの角丸でクリップする。

### 7.5 半透明合成の保証 (`EXT-024`)

**すべてのノードで正しいアルファ合成を行う。** 背景画像を敷く使い方では、その上に載る UI が半透明でなければ意味がない。

- ブレンドは `ALPHA_BLENDING` (ストレートアルファ) で統一
- 深度バッファを使わない。**描画順がそのまま重なり順**になる
- UITree の深さ優先・前順走査が描画順である

### 7.6 メモリ

| 制約 | 値 |
|---|---|
| 1 画像あたりのファイルサイズ上限 | 32 MB ([04-theme.md 6.4.3](04-theme.md#643-取得時の制約-sec-024-sec-025)) |
| テクスチャの最大辺 | 4096 px。超える画像は縮小してから GPU へ送る |
| 同時保持する画像テクスチャ数 | 32 枚。超えたら LRU で解放 |

4096x4096 の RGBA8 は 64MB を消費する。`NFR-002` (常駐 250MB) に対して無視できない量であり、**縮小の上限を設ける**。

## 8. レイアウト

制約を親から子へ、確定サイズを子から親へ返す 1 パスのアルゴリズム。

```
layout(node, constraints) -> Size
  ├─ 子に制約を配り
  ├─ 子のサイズを受け取り
  └─ 自分のサイズを返す
```

対応する配置は `layout.row` / `layout.column` / `layout.stack` / `layout.scroll` の 4 種類のみ ([03-uitree.md 3.6](03-uitree.md#36-layout--レイアウトノード))。Flexbox やグリッドは持たない。

### 8.2 既定のレイアウトは安定 ID から引く

テーマは寸法を**すべては書かない**。公式サンプル `midnight` には `nav.channel_list` の幅がなく、`chat.view` が「横の余りを埋める」ことも書かれていない。それでも意図どおりに並ぶ必要がある。

したがってレンダラが**安定 ID ごとの既定のレイアウト**を持つ。

| 項目 | 意味 |
|---|---|
| `axis` | 子の並べ方 (`Row` / `Column` / `Stack`) |
| `grow` | 親の主軸の余りをどれだけ取るか |
| `cross` | 交差軸での子の扱い (`Stretch` / `Start` / `Center`) |
| `width` / `height` | 既定の寸法。テーマの `width` / `height` が優先される |
| `scroll` | はみ出しを切り、スクロールできるか |
| `hugs_content` | 重ねの中で、**親いっぱいに広がらない**か (印だけ) |
| `follows_cross` | 交差軸の大きさを**決めない**。親が決めた分をもらうだけか |
| `anchor_end` | スクロール位置の既定が末尾か (メッセージ一覧) |

> ⚠️ **`follows_cross` は「広がりたい子」に要る。** `nav.user_panel` は左側の下に敷かれる帯であって、左側の幅を決めるのは
> サーバ一覧とチャンネル一覧のほうである。これが無いと、帯が入れ物いっぱいに広がろうとした分だけ `nav.sidebar` が広がり、
> `chat.view` に配る余りが無くなって**チャットが消える**。

> ⚠️ **この表は拡張 ABI ではない。** 変えても既存のテーマとプラグインは壊れない (見た目は変わる)。
> 安定 ID の追加・削除の規則 (`EXT-003`) とは別物である。

`EXT-014` (テーマによるレイアウトの上書き) が入るのは M2 で、そのときこの表は「テーマが何も言わなかったときの既定」になる。

### 8.3 主軸は 2 段階で配る

```text
[1] 余りを取らない子を先に測る      ← 実寸が決まる
[2] 残りを、余りを取る子で grow 比に応じて分ける
```

この順序でなければならない。`chat.message` は「アイコン (40px) + 本文 (残り全部)」であり、**本文の折り返し幅はアイコンの幅を引いたあとでなければ決まらない**。全員に同じ制約を配ると本文が横にはみ出す。

### 8.1 仮想化 (`NFR-007`)

`chat.message_list` と `nav.channel_list` は**画面内に見える範囲のノードのみを生成する**。

> ⚠️ **これは [03-uitree.md 7.1](03-uitree.md#71-とくに-3-番目が重要) の未確定論点である。**
> 画面外のメッセージはノードとして存在しないため、**プラグインはそこにパッチを当てられない**。
> M1 の実装前にこの制約を確定させ、プラグイン API のドキュメントに明記する。

## 9. 差分更新と再描画

### 9.1 `NFR-003` の現状

S1 の実測では p99 が **18.82 ms** で、VSync 周期 16.67 ms をわずかに超えた。約 1% のフレームで 1 フレーム落ちている。

原因の候補 (未特定):

- `ControlFlow::Poll` による busy loop と VSync 待ちの相互作用
- **毎フレームのインスタンスバッファ全体転送**
- Windows のコンポジタ (DWM) との同期

### 9.2 実装での方針

| 項目 | S1 の実装 | 実装での方針 |
|---|---|---|
| イベントループ | `ControlFlow::Poll` (常時描画) | `ControlFlow::Wait` + 明示的な再描画要求 |
| インスタンスバッファ | 毎フレーム全体を転送 | **変更のあった範囲のみ転送** |
| 再描画の契機 | 毎フレーム | 状態変化 / アニメーション / キャレット点滅のみ |

**`NFR-003` は M1 の実装後に再測定して判定する。**

### 9.5 アニメーションは時間で駆動する

「1 フレームごとに少しずつ近づける」書き方は簡単だが、**60Hz と 144Hz で速さが変わる**。`EXT-020` (全プラットフォームで同じ描画結果) を掲げている以上それは採れない。経過時間で位置を決める。

```text
  t = (いま − 始めた時刻) / 長さ
  出す値 = from + (to − from) × ease(t)
```

| | |
|---|---|
| 何が動くか | **確定したスタイルの値だけ。** 木の形は動かない |
| いつ回るか | **動いているあいだだけ。** 止まったら再描画の要求をやめて寝る (`NFR-005`) |
| 誰が動くか | テーマが `transition` を書いたノードだけ ([04-theme.md 3.3.2](04-theme.md#332-transition--飛ぶのではなく動く)) |
| 同一性 | 安定 ID と `key` の組。**木は毎フレーム組み直される**ので、これしか手がかりが無い |

> ⚠️ **初めて見たノードは動かさない。** 開いた瞬間に画面じゅうが動き出すのは見栄えではない。
>
> ⚠️ **途中で向きが変わったら、いま見えている値から引き直す。** 行き先から始めると一度飛ぶ。
>
> ⚠️ **消えたノードの記録は捨てる。** 残すと一覧をめくるたびに増え続ける。

**出たり消えたりするノードは滑らかにならない。** 選択の印のように「置くか置かないか」で切り替わるものは、動く対象が存在しない瞬間があるので、別の仕組みが要る。まだ無い。

### 9.6 絵が入らなくなったら、まとめて忘れる

棚詰めは**途中の 1 枚を空けられない**。要らなくなった 1 枚だけを抜けない以上、埋まったらまとめて忘れて詰め直すしかない。

| | |
|---|---|
| 忘れるのは | **絵の側だけ。** 文字の側は触らない — 本文が虫食いになるのは、顔が 1 枚消えるよりずっと悪い |
| 入れ直すのは | 取ってきた側。円盤に残っているので**網へは出ない** |
| 見え方 | 1 フレームだけ顔が消える |

> ⚠️ **入れた枚数が少ないうちは詰め直さない。** 入りきらない大きさのものを頼まれているなら、何度詰め直しても入らない。**詰め直しては溢れ、溢れては詰め直す**空回りになる。
>
> ⚠️ **頼む絵は描く大きさで頼む。** 40px で描くものを 128px で頼むと 10 倍の面積を食い、すぐ埋まる。実際に埋まった。

### 9.7 アトラスは足りなくなったらページを足す (R3)

1 ページ (2048²) が埋まったら、次のページを作ってそこへ詰める。**追い出さない** — 追い出すには「もう使っていない」を知る必要があり、それを知る仕組みのほうが高くつく。

| | |
|---|---|
| 1 ページ | 2048² × RGBA = **16MB** |
| 上限 | **4 枚 (64MB)**。公式 Electron 版より小さいという主張を保てる上限 |
| 詰める先 | **最後のページだけ。** 前のページに戻って隙間を探さない — 棚詰めの性質上、探す価値のある隙間はほとんど残らない |
| 描くとき | **ページごとに束を分ける。** 束ねは 1 枚のテクスチャしか指せない |

> ⚠️ **上限に達したら、そこから先は描けない。** そのときだけ虫食いになる。日本語と絵文字と顔を大量に見た後である。
>
> ⚠️ **ページを足すたびに束ね直す。** 束ね直さないと、新しいページに載ったものが描かれない。

絵の側は上限に達する前に[詰め直す](#96-絵が入らなくなったらまとめて忘れる)。**文字は詰め直さない** — 本文が虫食いになるのは、顔が 1 枚消えるよりずっと悪い。

### 9.8 絵は画面に出てから取りに行く

木を歩いて集めると、メンバー一覧に 300 行あれば 300 枚を取りに行く。**見えているのは 15 行ほど**である。

そこで「要る」と言うのは**描くところまで来たとき**にする。切り取りで消えた行も、潰れた枠も、そこへは来ない。

```text
  フレーム N    描く → 手元に無かった URL を控える
  フレーム N+1  控えたぶんを頼む → 届いたら描く
```

| | |
|---|---|
| 誰が決めるか | **レンダラ。** 見えているかどうかは配置と切り取りが決めることで、木を組む側は知らない |
| 見え方 | 巻いて出てきた顔が 1 テンポ遅れて出る (`<img loading="lazy">` と同じ) |

> ⚠️ **届いたことを「変わった」と数える。** イベントループは寝ているので ([`NFR-005`])、起こされたときに変化を申告しないとそのまま二度寝し、**届いた顔がいつまでも出ない**。

### 9.4 描けなかったフレームを取りこぼさない

`ControlFlow::Wait` には落とし穴がある。**サーフェスの取得に失敗したときに黙って帰ると、次の入力が来るまで窓が空白のままになる。**

`get_current_texture` は、ウィンドウの大きさが変わった直後・ディスプレイの構成が変わった直後 (ノート PC の蓋の開閉など) に `Outdated` を返す。毎フレーム描いている実装なら次のフレームで直るが、待って描く実装では次が来ない。

したがって:

| | |
|---|---|
| `Outdated` / `Lost` | サーフェスを再構成し、**その場でもう一度取得を試す** |
| それでも駄目 | 呼び出し側へ伝え、**再描画を要求し直してもらう** |
| `Occluded` (最小化・隠れている) | **再描画を要求しない。** 要求すると隠れている間じゅう回り続ける |

あわせて、**描く直前にウィンドウの実寸からサーフェスの大きさを合わせる**。リサイズの通知を取りこぼしてもサーフェスが古い大きさのままにならないようにするためで、大きさが同じなら何もしないので費用はない。

### 9.3 非アクティブ時 (`NFR-005`)

ウィンドウが非アクティブ、または最小化・オクルードされている間は描画を停止する。S1 で `Focused(false)` による停止を確認済み。

モバイルではバックグラウンド遷移で同じ扱いにする (`PLT-043`)。

## 10. GPU バックエンドの選択 (S1 の発見)

> **「対応していないバックエンドは `request_adapter` が `None` を返す」という前提は成り立たない。**
> S1 の検証機では Intel の Vulkan ICD がインスタンス生成中に**セグメンテーション違反を起こし、プロセスごと落ちた**。

### 10.1 探索対象を明示的に絞る

| OS | 候補 (優先順) | 探索しない |
|---|---|---|
| Windows | GL → DX12 | **Vulkan** |
| macOS / iOS | Metal | — |
| Linux | Vulkan → GL | — |
| Android | GLES → Vulkan | — |

Windows で GL を優先するのは S1 の実測による。

| バックエンド | WorkingSet | Private | 初フレームまで |
|---|---|---|---|
| DX12 | 309.4 MB | 285.7 MB | 845〜982 ms |
| **GL** | **69.7 MB** | **18.1 MB** | **332〜384 ms** |

同一バイナリ・同一シーンで **16 倍**の差がある。

### 10.2 起動時プローブ

初回起動時、**別プロセス**でバックエンドの初期化を試し、成功したものを設定に記録してから本体を起動する。ドライバのクラッシュがクライアント本体を巻き込まないようにする。

```
gumicord --probe-gpu          別プロセス。成功したバックエンド名を stdout へ
    │
[記録]  設定に保存
    │
[本体起動]  記録されたバックエンドのみを候補にする
```

利用者が手動で上書きできる設定も用意する。

### 10.3 コンピュートシェーダに依存しない

**描画にコンピュートシェーダを使わない。** 使うと GL / GLES バックエンドが選べなくなり、10.1 の表が崩れる。

これが `vello` を採用しなかった理由でもある ([02-architecture.md 2D 描画方式](02-architecture.md#2d-描画方式--s1-で確定))。

## 11. 性能予算

| 指標 | 目標 | S1 実測 (下限) | 要件 |
|---|---|---|---|
| コールドスタート | < 500 ms | 332 ms | `NFR-001` |

| フレーム時間 p99 | < リフレッシュ周期 | 18.82 ms (未達) | `NFR-003` |

| バイナリサイズ | < 30 MB | 4.66 MB | — |

**予算の配分** (常駐 250MB の内訳、暫定):

| 用途 | 予算 |
|---|---|

| 状態 + SQLite キャッシュ | 50 MB |
| プラグイン (11.3 KB × 想定 20 個) | 1 MB |
| その他 | 27 MB |

プラグインのフットプリントは S3 で実測済みで、**無視できる量**である。

## 12. 適合テスト (`NFR-015`, `EXT-020`)

**同一の UITree とテーマから生成された描画結果を、全プラットフォームでスクリーンショット比較する。**

```
テストケース = (UITree の固定サンプル, テーマ, ウィンドウサイズ, DPI スケール)
    │
各プラットフォームでオフスクリーン描画
    │
基準画像と比較 (許容差を設ける)
```

### 12.1 比較対象にしないもの

| 除外するもの | 理由 |
|---|---|
| システムフォントに依存するテーマ | 環境によって書体が違う ([04-theme.md 9 章](04-theme.md#9-ext-020-全プラットフォームで同一の描画結果-の限界)) |
| カラー絵文字 | OS ごとに絵文字フォントのデザインが異なる |
| ネイティブのタイトルバー | そもそも描画していない |

**同梱フォントのみを使うテーマ**に対してのみ厳密比較を行う。

### 12.2 許容差

GPU とドライバによってアンチエイリアスの結果が 1 階調ずれることがある。**ピクセル完全一致は要求しない。**

| 項目 | 許容 |
|---|---|
| 1 ピクセルあたりの色差 | 2/255 まで |
| 許容差を超えるピクセルの割合 | 0.1% まで |
